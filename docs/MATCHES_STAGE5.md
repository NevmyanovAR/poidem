# Этап 5: отклики и взаимные мэтчи

Исторический отчёт первоначального D49. Текущие правила заменены D50: повтор после отказа запрещён, чат встроен, добавлены архив и серверное «Все». Приоритет имеет [CHAT_ARCHIVE_STAGE5](CHAT_ARCHIVE_STAGE5.md); инструкции ниже о повторной попытке и обязательном username устарели


## Подтверждённые решения D49

До реализации проверены AGENTS, действующие документы, прежние модели и миграции. Задание закрывает B03: **одна подтверждённая пара на план**, ровно два участника. Использованы прежние users/profiles/photos/plans/plan_responses/matches, cookie-сессии, CSRF и PostgreSQL. Второй системы пользователей/планов нет.

Непосредственно блокировали этап B05/B07 (повторы/слоты/остальные отклики), B08 (нет username) и противоречие о деморежиме. Пользователь ответил:

- Деморежим остаётся удалённым; вымышленные данные только в автоматизированных тестах
- **До 15 одновременно ожидающих откликов разных людей**. Отказ освобождает слот; могут снова откликнуться тот же человек или новый. За всю историю плана разных людей может быть больше 15. Это новое уточнение заменяет прежнее ограничение 15 исторических людей
- Принятие создаёт одну пару и закрывает план. Остальные ожидающие получают `closed` / «Пара уже выбрана»; это не персональный отказ автора
- Username необязателен при регистрации. После мэтча выдаётся ссылка только на username второго участника из последнего подтверждённого Telegram-входа. При отсутствии — понятное состояние и инструкция задать username в Telegram, повторно войти и обновить данные

Сохранены D46: нельзя изменять/отменять план с историей откликов или встреч; физическое удаление планов, отзыв отклика и отмена мэтча сейчас не добавляются. Отклик/принятие разрешены только для доступного опубликованного будущего плана; принятие проверяет ту же версию условий, на которую откликнулся пользователь.

B02 не требует добавлять несогласованные фильтры географии/предпочтений. B06 — применять текущие статусы доступности, без придуманной модерации/жалоб. B13 — сохранять существующий отказ 409 на удаление аккаунта со связанной историей. Бот, опрос, рейтинг, аналитическая панель и production не входят в этап.

## API

Пути относительно `/api/v1`. Везде нужна настоящая серверная сессия, на записи также Origin/CSRF. X-Account-Context проверяет соответствие окна текущей cookie; клиентские Telegram ID/author_id/responder_id не принимаются как авторизация.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/plans/{id}/author` | Разрешённые публичные поля автора доступного плана |
| GET | `/plans/{id}/author/photo` | Текущее фото автора через тот же контекст |
| GET | `/plans/{id}/capacity` | Число ожидающих, максимум/остаток, can_respond, только собственный active response_id |
| POST | `/plans/{id}/responses` | Отклик; `{expected_plan_version}`, обязательный UUID Idempotency-Key |
| GET | `/plans/{id}/responses` | Отклики на конкретный план, только автору |
| GET | `/me/responses?direction=incoming\|outgoing` | Собственные входящие/исходящие попытки |
| GET | `/responses/{id}` | Один отклик только автору плана или откликнувшемуся |
| POST | `/responses/{id}/decision` | Только автор: `{decision:"accept"\|"decline", expected_version}` |
| GET | `/responses/{id}/profile/photo` | Фото второй стороны из активного разрешённого отклика |
| GET | `/me/matches` | Только свои мэтчи |
| GET | `/matches/{id}` | Подтверждённая пара, дата/зона/место принятой встречи |
| GET | `/matches/{id}/contact` | Контакт только второго участника после взаимного согласия |
| GET | `/matches/{id}/photo/author\|responder` | Фото участника только из собственного мэтча |

Списки имеют `items/next_cursor`, limit 1–50 и cursor до 512 символов. DTO не содержат чужих Telegram ID, private_username, предпочтений, роли, storage key, cookie, CSRF или сырого initData. Публичная анкета: name, age, bio, interests и photo:{url}; контакт не вкладывается в неё/каталог/отклик автоматически.

Повтор POST с тем же ключом возвращает прежний результат, даже если старая попытка уже отклонена. Новый ключ после отказа создаёт **новую строку попытки**; история не затирается. Два конкурентных ключа одного человека не создают два активных отклика. Повтор того же принятия/отказа возвращает текущее решение; противоположное решение или устаревшая версия ожидающего отклика — 409. Недоступные чужие записи — 404, отсутствие сессии — 401, Origin/CSRF — 403, заполненные 15 мест — 409 PLAN_RESPONSE_LIMIT.

## Модели и миграция 0004

Новых таблиц нет. У matches добавлен UNIQUE(plan_id). У plan_responses:

- прежний UNIQUE(plan_id,responder_id) заменён частичным уникальным индексом для waiting/accepted; завершённых попыток человека может быть несколько
- частичный уникальный индекс не допускает два accepted на один план
- прежние 15 уникальных slot_no и запрет собственного отклика сохранены
- declined/closed не держат слот; у closed нет decision_actor_id, но есть время закрытия
- принятие, Match со снимком согласованной версии/даты/зоны/места, закрытие плана и остальных ожидающих записей — одна транзакция

Порядок записи: блокировка текущего пользователя/перепроверка сессии, затем SELECT FOR UPDATE строки плана. Это сериализует отправку/решение с существующими изменением/отменой плана. Уникальные индексы дополнительно защищают БД. Если изменение плана успело первым, отклик со старой версией не принимается; если отклик первым — изменение запрещается D46.

Миграция не создаёт людей, планы или мэтчи. Старые declined освобождают slot_no без удаления истории. Если в прежней БД уже есть несколько мэтчей/принятых откликов на план, upgrade останавливается: записи не удаляются молча. Downgrade с повторными/закрытыми попытками запрещён до отдельного решения, чтобы не потерять историю.

## Доступ и интерфейс

У прежнего `/media/photos/{id}` доступ остаётся только владельцу. Новые фото не публикуются статическим CDN: каждый запрос проверяет текущую сессию, контекст, владельца анкеты, готовность/видимость фото и ограничения. После закрытия/отклонения отклика его фото больше не выдаётся через этот контекст. Участники мэтча пользуются отдельным разрешённым контекстом. Чужой UUID фото/отклика/мэтча доступа не даёт. Ответы и фото — no-store.

У заблокированных пользователей/анкет/фото доступ ограничен повторной проверкой на сервере. Неподтверждённая жалоба сама по себе ничего не блокирует. Автор может явно отклонить отклик с недоступной анкетой и освободить слот; принять его нельзя. Полный смысл будущих ограничений/жалоб остаётся B06.

People показывает реальные пять полей анкеты и план, серверный остаток слотов, «Пойдём?», ожидание/обновление и переход к другим планам. MyPlans использует прежние карточки/вкладки плюс «Полученные отклики»; «Выбранные» показывает исходящие попытки, «Мэтчи» — собственные пары. Экран мэтча использует сохранённые CSS, исходный PNG и две настоящие анкеты. Статические фотографии планов/редакционные идеи не превращаются в вымышленных людей.

Из визуальных стилей добавлены только перенос длинных пользовательских строк и обрезка длинной подписи на полароиде. Палитра, типографика, PNG и фотографии не менялись. Подпись в форме фото обновлена, потому что прежнее обещание «только твоему аккаунту» после разрешённого публичного просмотра стало неверным.

Клиент хранит данные только в памяти, получает серверные коллекции и очищает контекст при смене/потере авторизации. Ошибка API не подменяется вымышленными пользователями. Обновление/повторное открытие загружает данные PostgreSQL. Автоматических уведомлений бота пока нет.

Контакт: [официальные публичные username-ссылки Telegram](https://core.telegram.org/api/links#public-username-links). [ID-ссылки](https://core.telegram.org/api/links#id-links) не обещаются как универсальный переход клиента. Ссылка строится сервером только на t.me с разрешёнными символами, без произвольной схемы/query; frontend повторно ограничивает формат. Telegram-вход не проверяет реальную личность/возраст. Username может измениться вне приложения; повторный вход обновляет сохранённое значение, доступность переписки/приватность определяет Telegram.

## Ручной сценарий: два настоящих Telegram-аккаунта

1. На A и B открыть Mini App кнопкой бота, дождаться подтверждённого входа. Проверить собственные анкеты/фото; если анкеты нет, сохранить её с тремя интересами
2. A создаёт будущий план и явно публикует его. Если исчерпан дневной лимит, не сбрасывать его; использовать доступный план или дождаться новых суток
3. B открывает «Найти планы» → план A → анкету A. Сверить имя, возраст, фото, описание и интересы; контакта Telegram до согласия быть не должно. Собственный план не предлагается как чужой
4. B нажимает «Пойдём?». Видит ожидание. Повторное нажатие/обновление не создаёт второй активный отклик; повторное открытие сохраняет ожидание
5. A открывает «Мои планы» → «Полученные отклики», обновляет и видит анкету B. Для проверки повторов сначала нажимает «Отклонить»
6. B обновляет план, снова отправляет отклик. У A старая попытка остаётся «Отклонён», новая — «Ожидает ответа». В этом шаге расходуется только слот откликов, не дневная квота созданий планов
7. A принимает новую попытку. Открывается мэтч с двумя фото и точным временем/местом плана. План закрыт, других кандидатов принять нельзя
8. B открывает «Мои планы» → «Мэтчи» и обновляет. Открывает ту же встречу; закрытый план больше не предлагается в каталоге
9. Проверить переход в Telegram у обоих. Если username отсутствует, не должна появляться фиктивная ссылка. Установить username в Telegram у нужного участника, полностью закрыть/открыть Mini App кнопкой бота; второму участнику обновить данные мэтча
10. Старый приватный URL фото A из собственной анкеты по-прежнему не должен открываться под B (404), при этом разрешённое фото A в доступном плане/мэтче должно открываться. Cookie/initData/токен и персональные данные в чат/логи не копировать; достаточно статусов и описания результата

15 настоящих аккаунтов для ручного теста не нужны: предел/параллельность проверяют изолированные PostgreSQL-тесты. Тесты с третьим посторонним пользователем доказывают 404 на чужой отклик/мэтч/контакт/фото. Новая ручная проверка этапа 5 этим документом не объявляется выполненной.

- B02: география, фильтрация предпочтений/совместимости и дополнительные правила видимости; сейчас несогласованных фильтров нет

- B08: фактическая проверка открытия контакта в нужных клиентах Telegram и поведение при изменившемся username/приватности
- Бот, опрос, надёжность и административная аналитика — отдельные следующие этапы

Commit, push и production-деплой не выполняются. Результаты запусков дописываются после фактической проверки.
