# Этап 4: пользовательские планы

Дополнение D47 от 23.11.2026: серверный фильтр расширен на мат/оскорбления и явные опасные предложения с сохранением нейтральных обсуждений. Состав, ограничения и отдельный прогон — [CONTENT_FILTER](CONTENT_FILTER.md).

Реализовано 22.11.2026 на существующих FastAPI, PostgreSQL, SQLAlchemy и React. Авторизация на двух настоящих Telegram-аккаунтах завершена успешно по подтверждению пользователя; журнал — [TELEGRAM_MANUAL_TEST](TELEGRAM_MANUAL_TEST.md). Новые функции планов проверяются автоматизированно; отдельный ручной прогон этих функций на двух настоящих аккаунтах ещё нужно выполнить по инструкции ниже. Commit, push и production-деплой не выполнялись.

## Утверждённые правила D46

- Не больше 3 первых сохранений за календарные сутки **Europe/Moscow**, включая черновики. Редактирование и публикация не расходуют квоту повторно. Отмена и последующее отклонение не возвращают создание
- Квоту вычисляет backend; часы браузера, localStorage и удаление локальных данных не влияют на счётчик
- Обход удалением/повторной регистрацией не открыт: действующий DELETE аккаунта при планах/квоте/связанной истории возвращает 409 до решения B13. Персональные данные после успешного удаления не сохраняются в новой скрытой таблице. Изменение этой политики требует согласования хранения истории и защиты дневной квоты
- После сохранения план — черновик на сервере. Публикация — отдельная команда автора после валидации полей и фильтра. moderation_status остаётся not_submitted, это не одобрение модератора и не два этапа модерации
- Время встречи вводится в зоне устройства, передаётся RFC3339 со смещением и IANA time_zone, сохраняется UTC. В карточке отображается зона плана; форма изменения переводит время в текущую зону устройства, сохраняя момент встречи, если время не изменять
- Изменение/отмена разрешены автору до связанных откликов/мэтчей. При связях — 409. Отменённый/закрытый план не редактируется и не публикуется заново. Физического DELETE плана нет
- Демо остаётся удалённым. Синтетические анкеты/планы существуют только в автоматизированных тестах

## Что работает

Существующая форма сохраняет название (1–80 символов), категорию, описание (до 300 символов, необязательно), дату/время, место (1–160 символов). Все значения и автор проверяются сервером. Автор берётся только из сессии; переданные author_id, Telegram ID, статусы модерации и is_demo запрещены DTO. Для создания нужна сохранённая анкета; действие заблокированного аккаунта запрещено.

«Мои планы» загружает записи и статусы из PostgreSQL. Доступны явная публикация, изменение, отмена и просмотр деталей. Сохранение/публикация/изменение/отмена обновляют данные через API; кнопка «Обновить планы» позволяет второму аккаунту увидеть изменения. Каталог содержит только будущие опубликованные чужие планы активных пользователей. Черновики, собственные записи, отменённые/закрытые планы и pending/rejected/blocked модерации не выдаются. Редакционные идеи остаются отдельно во «Вдохновении»; на их основе можно заполнить форму, но это не пользовательская публикация.

Детали плана доступны автору либо авторизованному читателю опубликованного предложения. Из анкеты автора выдаются только внутренний UUID и отображаемое имя. Личные фото, Telegram ID/username и контактные данные не раскрываются. «Пойдём?» в карточке открывает детали, не создаёт отклик или мэтч. Разделы будущих откликов/мэтчей не имитируют знакомства.

Нет локального fallback для серверных планов или квоты. При недоступном API видна ошибка и доступен повтор загрузки. Без сессии показывается предложение войти; сохранить план локально вместо сервера нельзя. Очистка данных устройства не удаляет серверные анкеты и планы.

## API

Все пути относительно `/api/v1`. Все требуют сессию; запись также проверяет Origin и X-CSRF-Token.

Frontend передаёт X-Account-Context с внутренним UUID, полученным от сервера при подтверждённом входе. Если cookie сменилась на другой аккаунт, API планов возвращает 409 AUTH_CONTEXT_CHANGED до чтения данных. Этот заголовок — дополнительная проверка согласованности окна, не доказательство авторизации: actor всегда определяется серверной cookie. Без cookie один UUID доступа не даёт. Это закрывает случай двух окон с общим cookie jar.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/plans` | Чужой опубликованный каталог; category, limit 1–50, cursor |
| GET | `/plans/{id}` | Разрешённые детали, иначе 404 |
| POST | `/plans` | Первый серверный черновик, Idempotency-Key: UUID обязателен; 201 или 200 при повторе |
| PATCH | `/plans/{id}` | Частичное изменение; expected_version обязателен |
| POST | `/plans/{id}/publish` | Явная публикация; expected_version |
| POST | `/plans/{id}/cancel` | Отмена; expected_version |
| GET | `/me/plans` | Все собственные статусы; limit/cursor |
| GET | `/me/quotas` | maximum, used, remaining, day, time_zone, resets_at, policy_version |

Пример структуры POST (не настоящая публикация):

```json
{
  "title": "Кофе после музея",
  "category_code": "art",
  "description": "Встречаемся у входа",
  "starts_at": "2099-12-01T18:30:00+03:00",
  "time_zone": "Europe/Moscow",
  "place": "Вход в музей"
}
```

Категории: art, food, walks, experiences. Полные DTO — OpenAPI локального backend (`http://127.0.0.1:8001/docs`), в production документация отключена. Swagger без настоящей Mini App сессии не даёт доступа к частным API; копировать туда initData/cookie для обычной проверки не требуется.

Коллекции возвращают items/next_cursor с порядком по времени и UUID. Автор использует созданную сервером version в последующих командах; устаревшая версия — 409. Чужая запись — 404. Несогласованная операция при откликах/мэтчах — 409. Нет сессии — 401, чужой Origin/CSRF — 403, некорректные поля/содержание — 422, дневной лимит — 429 с Retry-After до следующей московской полуночи.

Один пользователь сериализует запись блокировкой user-row, а `daily_plan_usage` атомарно увеличивается через PostgreSQL UPSERT только при used < 3. Расход, план и idempotency record коммитятся вместе. Ошибка до коммита откатывает всё. COUNT → INSERT вместо защиты от гонки не используется.

Повтор POST с тем же actor/Idempotency-Key и телом возвращает ту же запись без расхода; другое тело с тем же ключом — 409. Запись содержит hash запроса и ссылку на ресурс, без копирования полного содержания в safe_result. Технический expires_at задан на сутки; пока запись существует, повтор возвращает существующий ресурс, автоматического удаления этой истории сейчас нет. PATCH/команды не получают автоматический сетевой повтор; версия защищает их от устаревшей записи. Клиент сохраняет ключ POST для повтора неизменённой формы.

## Схема и миграция

Используются прежние plans, daily_plan_usage, idempotency_records, categories и внешние ключи пользователей/откликов/мэтчей. Второй системы пользователей или повторных таблиц нет.

Revision **0003** после 0002 добавляет cancelled в CHECK публикации и четыре неперсональные категории с существующими изображениями. Таблиц по-прежнему 29. При downgrade с отменёнными планами требуется отдельное решение; миграция не переводит их молча в другой статус и не удаляет категории с возможными ссылками.

Текстовый фильтр — `backend/src/poidem/services/plan_content.py`: расширяемые правила, NFKC/casefold, удаление скрытых форматных символов, нормализация разделителей, простые омоглифы/написание по буквам. Название, описание и место проверяются отдельно и в сочетании. Границы слов и формы существительных защищают от блокировки «стрипсов», «клубники», «заводного механизма». Причина возвращается без копирования пользовательского адреса в логи. Фильтр не определяет намерение человека и не заменяет будущую модерацию.

## Проверка на двух настоящих аккаунтах

1. Откройте Mini App кнопкой бота на A и B; дождитесь подтверждения входа. Если A удалён в предыдущем тесте, сначала заполните новую тестовую анкету и фото
2. На A создайте план с будущей датой и безопасным местом. «Сохранить план» должен открыть «Мои планы» со статусом «Черновик»; счётчик уменьшится на один
3. Полностью закройте/откройте A: черновик должен восстановиться. На B нажмите «Обновить планы» — черновик A пока не виден
4. На A нажмите «Опубликовать». На B обновите каталог: план A должен появиться с категорией, временем/зоной, местом и именем автора. На A в каталоге собственный план не показывается, он остаётся в «Моих планах»
5. На B откройте карточку: доступны детали плана, но нет чужого приватного фото, контакта, фиктивного отклика/мэтча
6. На A через «Изменить» поменяйте название или будущую дату. На B обновите каталог: изменение видно; used у A не изменился
7. На A отмените план и подтвердите действие в диалоге. У A статус «Отменён», у B после обновления план исчез. Квота не возвращается
8. Создайте оставшееся до трёх число планов (черновики тоже считаются). При нуле UI блокирует создание; сервер также возвращает 429 при прямом POST. Если уже были сегодняшние создания, учитывайте их; не сбрасывайте счётчик SQL/удалением данных
9. Проверьте запрещённые темы в названии, описании и месте: ошибка объясняет причину, поля не исчезают, расхода за неуспешное создание нет. Безопасный текст со «стрипсами» или «клубникой» не должен блокироваться
10. Перезапуск A/B восстанавливает их собственные записи. У второго аккаунта отдельная квота. Очистка данных устройства не удаляет серверные планы и не обнуляет лимит

Прямой POST без сессии, подмена автора/версии и гонки проверяются автоматически ниже. Не переносите авторизационные секреты в PowerShell/чат для ручной проверки.
