# Решения, предложения и открытые вопросы

D45, 22.11.2026: по просьбе пользователя сокращено ожидание входа после смены туннеля. Пока внешний SDK не загружен, frontend передаёт исходную строку из параметра запуска tgWebAppData, который использует официальный SDK, без пересборки и сохранения в storage. Наличие строки не даёт авторизации: HMAC/auth_date проверяет только backend, затем клиент обязательно подтверждает cookie и совпадение пользователя через /auth/csrf. На весь вход разрешён один автоматический повтор сетевой ошибки или HTTP 502/503/504; отказы подписи/прав/лимитов и устаревший контекст аккаунта не повторяются. Тайм-аут запроса не сокращался. Фиксированного времени входа не обещаем: новая ссылка имеет другую host-only cookie, а задержки Quick Tunnel/VPN остаются внешним фактором. Постоянный домен и production-размещение не настраивались.

D44, 20.11.2026: пользователь разрешил временный Cloudflare Quick Tunnel для ручного тестирования настоящей Telegram-авторизации (этап 3.5). Один HTTPS-origin через Vite 5173 → /api → backend 8001, Secure/HttpOnly/SameSite=Lax, PostgreSQL на loopback. Разрешение не включает production, commit/push или разработку планов/мэтчей. Демо остаётся удалённым. Результаты и запуск — [TELEGRAM_MANUAL_TEST](TELEGRAM_MANUAL_TEST.md).

D43, 20.11.2026: пользователь отменил демонстрационный режим целиком. Удалены провайдер/fixtures/переключатель/заполнение примером и симуляции. Предыдущие D-решения о сохранении demo и соответствующие части D39 заменены этим уточнением. Синтетические данные автоматизированных тестов не являются режимом приложения.

## Уточнение безопасности от 18.11.2026

Подтверждено прямым заданием, уточняет ранние документы:

- D28: Telegram-авторизацию для реальных пользователей подтверждает только backend: подпись и возраст initData, привязка к Telegram ID, запрет подмены и неавторизованной публикации. На frontend — типизированное состояние и честная подпись unverified; SDK и тестовая анкета не подтверждают личность
- D29: двухэтапная модерация, жалобы на пользователей/планы и блокировка нарушителей входят в будущий MVP. Смысл этапов и порядок действий не определены; текущие статусы не моделируют выдуманные этапы, UI не содержит фиктивных действующих жалоб/блокировок
- D30: максимум 15 разных откликнувшихся на план, без автора и повторов; максимум 3 создания плана на пользователя за календарный день. Единственный frontend-конфиг — `src/config/planRules.ts`, затем авторитетные настройки и атомарное применение переносится на backend
- D31: проверка названия/описания по расширяемым правилам запрещает заданные тематики, сохраняет введённое и показывает ошибку. Это быстрый клиентский фильтр, не подтверждение модерации; backend проверяет независимо
- D32: надёжность отображается отдельным компонентом; значения в `src/data/demo.ts` вымышленные, без формулы. Отклик, молчание в опросе и неподтверждённая жалоба не являются причиной автоматического штрафа
- D33: десктопное приветствие сохраняет исходное `/images/gallery.jpeg`, полный оригинальный PNG, согласованные шрифты и палитру. Фотография и контент занимают одну явную область CSS grid; размытие 1.5 px только на фото, градиент отдельный, мобильные правила приветствия сохранены

Технические допущения прототипа: счётчик созданий использует `createdAt` сохранённых собственных записей, включая черновики, и календарь устройства (подписан в UI). Публикация существующего черновика не создаёт вторую запись. Старые записи без даты не датируются задним числом. Счётчик откликов показывает уникальных людей в истории; операции освобождения места нет. Эти допущения не закрывают Q20–Q21, не задают итоговую серверную политику и обходятся изменением localStorage/часов. Ручной сброс тестовых данных не является разрешённым сбросом серверной квоты.

## 2. Предложения — ещё не утверждены

Уточнение пользователя от 17.11.2026: сохранить первоначальный вид с белым основным текстом и голубыми выделениями, используя точные фирменные HEX-коды. Удалить все упоминания версии и имитации из пользовательского интерфейса, включая плашки, кнопки, уведомления, alt и metadata. Это уточнение заменяет прежнее требование о светло-голубом основном тексте и видимых служебных пометках. Технические ограничения статического frontend сохраняются и описаны в документации.

### P01. Простой модульный монолит

Один репозиторий, один Python-проект, общая прикладная логика для FastAPI и обработчиков aiogram, одна PostgreSQL. Внутри можно разделить код по обязанностям: анкеты, планы, согласия/мэтчи, уведомления/опросы и аналитика. Frontend обращается к API; авторизацию, права и взаимность проверяет сервер.

Способ исполнения бота (polling или webhook), фоновых задач и число процессов выбрать на техническом этапе. Отдельный процесс из того же проекта при необходимости не требует отдельного сервиса с собственной БД. Не добавлять Redis, брокер, Kubernetes, отдельный сервис аналитики или BI по умолчанию. Миграции и библиотеку доступа к данным выбрать при реализации; ORM ещё не назначена.

### P02. Минимальная модель совместимости

Начать с явно общего сценария/плана и взаимно подходящих предпочтений; для конкретной встречи проверять согласованные дату, время и место. Не вводить нечёткий подбор по похожести интересов или расстоянию. Требуется решить, выбирают ли люди одну общую карточку встречи или независимые экземпляры одного сценария (Q03). Это предложение, а не уже заданный алгоритм.

### P03. Целостность и устойчивость

Создание мэтча выполнять транзакционно; обеспечить уникальность согласия и мэтча в согласованном контексте средствами PostgreSQL. Для запланированных уведомлений и опросов рассмотреть хранение статуса/времени отправки в той же БД с восстановлением после перезапуска. Не обещать абсолютную доставку ровно один раз при внешнем сбое: определить допустимые повторы и обработку неопределённого результата отправки. Точная модель зависит от Q04 и Q08.

### P04. Измерения для диплома

Гипотезы-кандидаты: выбор занятия помогает перейти к взаимному интересу; часть мэтчей приводит к реальным встречам; предложенный досуг получает положительную оценку. Источники описывают проблему, но не доказывают эти гипотезы и не задают порогов успеха.

Предлагаемая воронка: завершил анкету → выбрал/создал план → выразил согласие → стал участником мэтча → нажал переход в Telegram → ответил на опрос. Возможные показатели: число пользователей/планов, популярность сценариев, доля пользователей с мэтчем среди выбравших план, число парных мэтчей, доля ответивших на опрос, доля «Да» среди ответов, распределение оценок.

Пользователей считать отдельно от мэтчей и ответов. Для встречи различать «оба ответили да», «хотя бы один да», «ответы расходятся» и «данных недостаточно»; не выбирать один вариант без Q10. Переход в Telegram — только нажатие/попытка открытия, не прочитанное сообщение. Мэтч и наступление даты не доказывают встречу. Хранить минимальные данные для согласованных показателей; внешний трекер и сбор переписки не предлагаются.
