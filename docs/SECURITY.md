# Безопасность серверного MVP

D48: полный клиентский фильтр проверяет текст локально при вводе; публичный снимок содержит только словарь/правила, без секретов/пользовательских данных. Сервер повторно проверяет все записи, включая прямой API. Синхронность обеспечивают экспорт и общий корпус, клиент не заменяет серверную защиту. Нейтральные обсуждения разрешены, новые запреты локаций — [CONTENT_FILTER](CONTENT_FILTER.md).

Этап 4: ручная Telegram-проверка двух аккаунтов завершена успешно по подтверждению пользователя. Планы подключены к той же серверной сессии: чтение авторизовано, запись проверяет Origin/CSRF, автор из actor, extra-поля запрещены, чужие изменения/непубличные детали — 404. Квота и идемпотентность транзакционные, никакой обход через localStorage не добавлен. Детали и принятые D46 ограничения — [PLANS_STAGE4](PLANS_STAGE4.md). Отклики/мэтчи и контакты не открываются этим этапом; старые описания отсутствующих API ниже исторические.

Последнее изменение D43: демонстрационный путь удалён целиком, серверный источник единственный. Старые три localStorage-ключа очищаются без чтения. Синтетические подписи/анкеты остаются только в изолированных тестах, не в runtime/bundle. Нет клиентского способа включить фиктивную авторизацию, публикацию или мэтч. Последующие упоминания DemoRepository описывают прежнюю архитектуру и не являются действующим требованием.

Статус 20.11.2026: реализованы каркас и Telegram-вход/сессии/CSRF, права собственной анкеты, безопасные приватные фото и удаление аккаунта/всех сессий. Подделка, истечение, IDOR, Origin/CSRF и изоляция проверяются автоматизированно с PostgreSQL. Реальный HTTPS-вход в Telegram пока не проверен. [TELEGRAM_AUTH](TELEGRAM_AUTH.md) описывает текущую реализацию; бизнес-права планов/мэтчей, модерация, бот и admin UI далее остаются требованиями будущих этапов. B-вопросы — [архитектура](BACKEND_ARCHITECTURE.md), endpoints — [контракт](API_CONTRACT.md), таблицы — [схема](DATABASE_SCHEMA.md).

## 1. Подтверждённые границы и предлагаемые меры

Подтверждено пользователем: серверная Telegram-авторизация, отдельные реальные и демонстрационные данные, серверные лимиты, модерация, взаимный парный мэтч, закрытые контакты, защищённая административная панель. Клиентский Telegram ID, localStorage и скрытая кнопка не являются средствами защиты.

Cookie-сессии, приватный файловый каталог, Origin/CSRF и обработка фотографий реализованы по текущему заданию. Настраиваемые defaults и ограничения описаны в TELEGRAM_AUTH. Итоговые домены, moderation workflow, сроки хранения будущей совместной истории и административные права ещё требуют согласования.

## 2. Telegram-вход и серверная сессия

### Проверка входа

1. Frontend передаёт только исходную строку initData в `POST /api/v1/auth/telegram` по HTTPS: из `Telegram.WebApp.initData`, а до загрузки SDK — из исходного параметра запуска `tgWebAppData` в URL fragment. Это тот же источник, который разбирает официальный SDK. Данные из обоих источников недоверенные до серверной проверки; наличие SDK или fragment не даёт прав. Строка не пересобирается, не записывается в storage, полный URL с параметрами запуска не журналируется. Отсутствие строки означает отсутствие подтверждённого входа: обычный браузер показывает доступное неавторизованное состояние, не получает фиктивную сессию и не падает.
2. Сервер ограничивает тело, строго разбирает параметры, отклоняет дубли ключей/повреждённое кодирование. HMAC реализован стандартными hmac/hashlib по официальному протоколу, сравнение compare_digest. Aiogram здесь не нужен: бот будет отдельным этапом в том же Python-проекте. HMAC включает все поля кроме hash, в том числе signature; схема Ed25519 третьих сторон не смешивается с ним.
3. auth_date проверяется отдельно: defaults 300 секунд давности и 30 секунд допуска в будущее настраиваются через env. Проверяются обязательные поля, типы и допустимый Telegram user ID. Сессия по умолчанию 86400 секунд; корректная подпись сама по себе не означает свежесть.
4. Пользователь определяется только из проверенного содержимого. Переданный отдельно `telegram_user_id`, `initDataUnsafe`, username, имя или фотография не дают прав. Telegram-вход подтверждает происхождение данных, не паспортную личность, возраст или прохождение модерации.
5. Проверенный Telegram ID однозначно связан с внутренним UUID. Одновременные входы не создают дубль пользователя благодаря UNIQUE в PostgreSQL. Заблокированный пользователь не получает доступ к запрещённым действиям.

Не смешивать HMAC-проверку владельцем бота с отдельным алгоритмом Ed25519 для третьих сторон. Правила построения проверяемой строки берутся из соответствующего официального алгоритма, а не из неполного примера. Секретные сравнения выполняются безопасным helper. Повторно использованное, но ещё свежее `initData` не является доказательством нового действия пользователя; политику повторного входа и отзыва сессий согласовать в B14.

Основания: [Telegram: проверка Mini App данных](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app), [aiogram: безопасный разбор initData](https://docs.aiogram.dev/en/latest/utils/web_app.html).

### Сессии и CSRF реализованы, публичные домены ещё не настроены

- Случайный непрозрачный идентификатор сессии хранится только в HttpOnly cookie; в БД — его криптографический hash, пользователь, сроки и отзыв. JWT и хранение токена в localStorage для этого MVP не требуются.
- Предлагаемая production-cookie: `__Host-poidem_session; Secure; HttpOnly; SameSite=Lax; Path=/`, без `Domain`. Перевыпуск после входа; logout отзывает запись и удаляет cookie. Сроки и правила параллельных сессий — B14.
- На каждом защищённом запросе проверяются срок, отзыв, актуальное состояние пользователя и права на конкретный объект. `GET /me` может сообщать собственный статус ограничения; это не даёт доступа к чужим данным.
- Изменяющие запросы требуют случайный CSRF-токен сессии, на frontend только в памяти, в заголовке X-CSRF-Token. Без HttpOnly cookie он не даёт входа. Проверяются точный Origin и тип тела. Login проверяет Origin/JSON; Fetch Metadata не используется как blanket-запрет cross-site, поскольку адрес API может быть отдельным. SameSite не заменяет CSRF-защиту.
- Персональные API-ответы и медиа: `Cache-Control: no-store`; никакого общего CDN-кеша для `/me`, мэтчей, контактов и фотографий анкет.

Предпочтительная схема размещения — один HTTPS origin с `/api` через шлюз к FastAPI. Тогда frontend может остаться статическим, а cookie не зависят от стороннего домена API. Конкретный шлюз и хостинг ещё не выбраны, их настройка не входит в этот этап.

Альтернатива — согласованные поддомены одного собственного сайта с точным credentialed CORS, CSRF и проверкой в Telegram/iOS. Связка `*.pages.dev` и постороннего API-домена может зависеть от ограничений сторонних cookie; простая замена на `SameSite=None` не гарантирует работу. Публичная конфигурация B14 должна быть проверена до пилота; локальные сессии уже реализованы. При credentials нельзя разрешать все origins через `*`: [FastAPI CORS](https://fastapi.tiangolo.com/tutorial/cors/).

Локально реализован Vite proxy /api → http://127.0.0.1:8001. HTTP-cookie с отдельным именем разрешена для development; production требует Secure. MINI_APP_URL/API_PUBLIC_URL/VITE_API_BASE_URL настраиваются, но не создают Pages proxy. HTTPS-доступ для проверки в Telegram будет настроен отдельно пользователем; обхода «войти по Telegram ID» нет. Для cross-site cookie SameSite=None обязательно Secure, и дополнительно нужна проверка ограничений Safari/iOS.

## 3. Права и административная панель

Права проверяет сервисный слой API/бота, а не маршрутизатор React. Роль администратора берётся из серверной БД после настоящего входа. `role`, `author_id`, результаты модерации, рейтинг и чужой ID не принимаются как поля пользовательских команд.

| Объект / действие | Минимальная граница доступа |
| --- | --- |
| Изменение анкеты, фото, собственный черновик | Только владелец; photo_id обязан принадлежать этому пользователю. |
| Каталог и анкета автора | Только данные, разрешённые политикой публикации/совместимости B02/B06; черновики и непройденная модерация не становятся публичными автоматически. |
| Входящие отклики | Автор соответствующего плана. Другой откликнувшийся не видит их список. |
| Принятие отклика | Только автор, актуальный waiting-отклик, атомарная проверка версий и состояния. |
| Мэтч и Telegram-контакт | Только два участника конкретного мэтча. Знание UUID не даёт доступа третьему. |
| Опрос / ответ | Только участник, для которого создано приглашение к опросу; нельзя ответить за партнёра. |
| Администрирование и аналитика | Отдельное серверное право администратора; обычному пользователю запрещено, даже при прямом HTTP-запросе. |

Для чужих закрытых объектов предлагается единообразный 404 без раскрытия существования. Применяются минимальные DTO: никакого Telegram ID, предпочтений или контактных данных в общедоступной карточке. Администратор получает только поля, необходимые для конкретной задачи; доступ к панели не должен автоматически открывать все Telegram-контакты.

Первое назначение администратора предлагается выполнять отдельной служебной CLI-командой оператором после проверки личности. Открытого endpoint для повышения собственной роли нет. Роли модератора/аналитика, список администраторов, дополнительная проверка входа и политика доступа к панели — B11. Не создавать универсальную панель редактирования всех таблиц с обходом бизнес-правил. Каждое изменение блокировки/модерации журналируется с актором, причиной, целью, версией и временем, в одной транзакции с действием.

## 4. Серверные данные и удалённый демонстрационный режим

- ApiProvider — единственный источник состояния; API определяет пользователя по проверенному Telegram-входу и серверной cookie
- Вымышленные анкеты, публикации, отклики, мэтчи, рейтинги, переключатель и заполнение примером удалены. Сетевые ошибки не подставляют людей/согласия. Редакционные идеи не являются пользовательской выдачей
- Demo-флаги и локальные симуляции удаляются без разбора/импорта; обычный legacy-профиль игнорируется, удаление только по явной очистке/удалению аккаунта. URL и старые флаги не включают режим. Настоящие анкеты/фото/сессии/согласия/квоты в localStorage не сохраняются
- Подтверждённый локальный сброс очищает временные черновики и старые данные прототипа на устройстве, сохраняя серверный аккаунт и сессию. Для удаления аккаунта есть отдельное подтверждаемое действие
- Синтетические подписи/анкеты допустимы только в автоматизированных тестах на отдельной проверенной PostgreSQL *_test. Тестовые SDK не добавляют production-обходы авторизации

## 5. Контент и фотографии

Фильтр выполняется на сервере при создании, редактировании и публикации. Помимо стрип-клубов/заброшенных зданий D47 согласовал мат/прямые оскорбления, угрозы/ненависть, предложения наркотиков, сексуальных услуг и мошенничества; нейтральные обсуждения и обычные бары/алкоголь разрешены. Проверяются название, описание и место отдельно/совместно, словоформы и простые маскировки. Ввод не переписывается; клиент получает генерируемый публичный снимок полного словаря/шаблонов, проверяет ввод локально и показывает серверную причину при отказе API. Текст не отправляется внешним сервисам и не кэшируется глобально. Отказ — не бан, не одобрение модератора и не гарантия безопасности. Границы и тесты — [CONTENT_FILTER](CONTENT_FILTER.md).

Клиент не может прислать `approved`. Решение модерации относится к версии контента: редактирование не наследует одобрение старой версии. Точное устройство ранее запрошенных двух этапов модерации не определено; Telegram-вход плюс фильтр нельзя самовольно назвать этими этапами. Жалоба — основание для рассмотрения, не доказательство нарушения, не автоматический штраф надёжности. Переходы статусов, повторное рассмотрение и судьба старых мэтчей при блокировке — B06/B10.

Предлагаемые меры для фото анкеты:

1. Multipart-upload с ограничением размера запроса на входе. Текущий прототип принимает JPEG/PNG/WebP до 3 MiB; перенос этого ограничения на сервер и предел разрешения согласуются в B01.
2. Проверка сигнатуры и декодирование изображения, ограничение числа пикселей/ресурсов. Расширение и клиентский MIME не являются доказательством. SVG, произвольные remote URL и пути файлов не принимаются.
3. Повторное кодирование в разрешённый растровый формат, удаление EXIF и иных ненужных метаданных. Ошибка декодирования означает отказ, а не сохранение «как есть».
4. Случайный storage key, приватный каталог вне `frontend/public`, защита от path traversal. Привязка владельца проверяется в БД и сервисе. Выдача только через авторизованный media endpoint с корректным Content-Type, `X-Content-Type-Options: nosniff` и без общего кеша.
5. Состояния processing/модерации учитываются до использования фото в публичной анкете. Staging-файл, запись БД и файловая система не образуют одну ACID-транзакцию: нужны безопасная финализация, компенсация и уборка оставшихся файлов по согласованному B13 сроку.

Оригинальные дизайн-фото и PNG-логотипы остаются статическими ресурсами; пользовательские фото отделены от них. Право использовать предоставленные фотографии и Nicoletta Script в публичном продукте нужно проверить до пилота, не подменяя его технической проверкой загрузки.

## 6. Бот, фоновые задачи и опросы

- Предлагается один polling-процесс aiogram с серверным bot token. Режим webhook возможен после B14; тогда проверяются его secret и допустимый входящий маршрут. Запуск двух конкурирующих polling-получателей запрещён конфигурацией развёртывания.
- Связь аккаунта с приватным чатом берётся из Telegram update и проверенной идентичности, не из присланного frontend `chat_id`. Разрешение писать боту проверяется по реальному результату Telegram; доступ не предполагается по наличию аккаунта.
- Update дедуплицируется по bot key/update_id. Callback опроса связан с конкретным адресатом, участником и сроком, проверяется `from.id`. Используется непрозрачный ограниченный токен с hash в БД либо равнозначная защищённая схема, без доверия к ID в callback.
- Состояние опросов хранится в PostgreSQL; in-memory FSM не является источником истинных ответов после перезапуска.
- Outbox записывается вместе с мэтчем/другим событием одной транзакцией. Worker берёт короткий lease, выполняет сетевой запрос вне транзакции и фиксирует результат; есть ограниченные повторы, backoff и состояние ошибки. Сбой отправки не отменяет мэтч. Перед поздней отправкой повторно проверяется актуальность встречи/прав.
- Отправка Telegram не даёт строгой гарантии exactly-once: при неопределённом результате после сбоя возможен повтор. Это нужно явно обрабатывать и отражать в журнале, а не обещать невозможность дублей.
- Отказ пользователя, недоступный чат, отзыв разрешения или ошибка Telegram не считаются неявкой и не снижают рейтинг. Ответ «встретились» — самоотчёт участника; молчание и разногласие не превращаются в установленный факт.

## 7. Конкурентные запросы и инфраструктура

Лимиты проверяются транзакционно: счётчик 3 в день с согласованной зоной/событием расхода B04; не более 15 допустимых слотов откликов с политикой освобождения B05. Повторы защищены UNIQUE и идемпотентностью. Принятие отклика, ровно два участника мэтча и outbox фиксируются атомарно. На повторах команды повторно проверяются права; идемпотентный ответ не должен выдавать персональные данные после отзыва доступа.

Дополнительные технические rate limits для входа, загрузки и частых запросов задаются конфигурацией, отдельно от бизнес-лимитов. Они должны действовать на уровне шлюза или общего серверного состояния; счётчик памяти одного процесса не даёт общей защиты нескольких workers. Ограничиваются тела, время запросов и дорогая обработка фото; доверенные прокси и Host/Origin задаются явно.

SQLAlchemy использует параметризованные запросы. Никаких SQL-фрагментов из пользовательской сортировки/фильтра. API runtime-role не имеет DDL/superuser-прав; миграции выполняются отдельным операторским шагом. PostgreSQL и приватное файловое хранилище не открываются в интернет. AsyncSession не разделяется между параллельными задачами. Секреты не включаются в Docker image или frontend bundle.

Предлагаемые заголовки браузерной защиты: запрет MIME sniffing, ограничение referrer и CSP с учётом реального Telegram embedding. Политику `frame-ancestors` нельзя выбирать так, чтобы сломать Mini App; её проверяют в согласованных клиентах до выпуска. Никакие изменения CSP/хостинга в этом этапе не выполнены.

## 8. Конфигурация, журналы и хранение

Имена ниже — будущая спецификация, не готовый `.env` и не набор окончательных значений:

| Группа | Что потребуется |
| --- | --- |
| Секреты | `TELEGRAM_BOT_TOKEN`, `DATABASE_URL`, изолированный `DATABASE_URL_TEST`, отдельные права мигратора; случайные session/CSRF токены генерируются сервером. |
| Адреса | `APP_ENV`, `MINI_APP_URL`, `ALLOWED_ORIGINS`, `TRUSTED_HOSTS`, параметры доверенного reverse proxy. `VITE_API_BASE_URL` может содержать только публичный адрес. |
| Вход | `INIT_DATA_MAX_AGE_SECONDS`, `AUTH_CLOCK_SKEW_SECONDS`, `SESSION_TTL_SECONDS`; значения после B14. |
| Медиа | `MEDIA_ROOT`, лимиты байтов/пикселей/форматов, лимиты обработки; значения после B01/B13. |
| Политики | Часовой пояс и событие расхода квоты, политика слотов, версии модерации/опроса/надёжности — только после соответствующих B-вопросов. |
| Worker | Lease, интервалы/предел повторов и параметры polling/webhook; точные настройки проверяются в тестовой среде. |

Секреты находятся в серверном окружении/закрытом хранилище, отсутствуют в Git, `VITE_*`, логах и примерах. В `.env.example` добавляются только имена и безопасные пустые значения при реализации. При отсутствии обязательной серверной настройки запуск завершается понятной ошибкой, без перехода к демоавторизации.

Журналы используют request_id, внутренний actor ID, тип события и безопасный код ошибки. Не журналируются raw initData, cookie, bot token, CSRF/callback токены, тела анкет, фотографии, контакты и сырые updates. Обработчики ошибок, включая validation errors FastAPI, не возвращают исходный чувствительный input, traceback или SQL. Аудит ограничен по доступу и не заменяется обычным debug-логом.

Для диплома собираются только согласованные события/агрегаты B12. Встреча, успешное открытие Telegram и факт переписки — разные вещи; клик ссылки не доказывает общение. Замена Telegram ID hash-значением сама по себе не означает обезличивание. Сроки хранения, согласия, доступ к данным, удаление, резервные копии и права на медиа — B13, до пилота. Нельзя молча выбрать бессрочное хранение или каскадное удаление аудита.

План восстановления должен согласованно охватывать PostgreSQL и приватные фотографии, включать ограничение доступа к копиям и проверку восстановления на отдельной среде. Резервная копия без фактической проверки восстановления не считается проверенной.

## 9. Обязательные будущие проверки

| Риск | Проверка перед включением реального сценария |
| --- | --- |
| Поддельная/просроченная авторизация | Изменённый user/hash, другой bot token, нет hash/auth_date, дубли параметров, старое/будущее время, пустое initData; нет выданной сессии. |
| Кража полномочий / CSRF | Поддельная роль, чужой Origin, отсутствующий/чужой CSRF, отозванная/истёкшая сессия, смена пользователя; нет мутаций. |
| IDOR и утечка контакта | Минимум три аккаунта: чужая анкета на запись, чужое фото/черновик/отклик/мэтч/контакт/опрос; нет доступа даже по известному UUID. |
| Обход лимитов / повтор согласия | 4+ создания, 16+ откликов, конкурентные accept, повтор ключа с другим телом, откат транзакции после расхода; проверяется конечная БД. |
| Вредоносное фото / контент | Поддельный MIME, повреждённый/слишком большой файл, decompression bomb, EXIF, чужой photo_id, варианты обхода запрещённых тематик и ложные совпадения. |
| Обход модерации | Подмена approved, изменение после одобрения, решение на устаревшую версию, заблокированный участник; проверяются утверждённые переходы. |
| Смешение демо и реального | Нет API-мутаций в деморежиме, нет автопереноса localStorage, нет демоответа при 503, поздний ответ не заменяет новый режим. |
| Ошибка бота / опроса | Чужой callback, повтор update, перезапуск worker, истёкший lease, Telegram error/запрет сообщений; нет чужого ответа или потери мэтча. |
| Админ-доступ и аналитика | Обычный пользователь не получает admin API; действия администратора аудируются, показатели сверяются на заранее рассчитанных данных. |
| Утечки / восстановление | Проверка логов, bundle и ошибок на секреты/PII; восстановление тестовых БД и медиа; проверка cookie в реальных Telegram/iOS/Android клиентах. |

Таблица — план проверок полного MVP. Следующий отчёт относится только к прошлому этапу 3.2; актуальные auth/profile проверки — TELEGRAM_AUTH. На этапе 3.2 выполнены 62 теста каркаса на Windows и в Linux-контейнере: ограничения/права БД, закрытый набор маршрутов, CORS/Host, безопасные ошибки и логи, health и Windows loop. На том этапе Telegram-подпись/сессии/ownership ещё отсутствовали; затем они реализованы и проверены для собственных анкет/фото. Moderation workflow и доставка остаются будущими этапами. Не засчитывать проверки отсутствующих маршрутов за готовую защиту будущих бизнес-команд. Полный фактический отчёт — BACKEND_IMPLEMENTATION.
