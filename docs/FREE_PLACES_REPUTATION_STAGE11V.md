# Этап 11В — свободные места и положительная репутация (D67)

## Подтверждённый объём

Задание от 28.11.2026 заменяет обязательный выбор/предварительное одобрение D66. Пользователь вводит название и адрес; публикация не зависит от проверки места. Это не новый каталог и не возврат к внешним Places API. Существующие PublicPlace, place_selections, CSV-инструмент и их данные остаются в «Сохранённом каталоге» административного раздела; одобрение каталога автоматически не подтверждает адрес конкретного плана. Старые миграции 0011–0013 не меняются.

Фото и взаимные подтверждения встреч остаются прежними, добавляются только независимые добровольные положительные впечатления. Никаких отрицательных оценок, санкций, автоматического определения личности или безопасности. Демо, backend-авторизация по Telegram ID клиента, публичные ссылки на фото не добавляются.

## Место и совместимость

Новый интерфейс — компактный единый блок «Где встречаемся?» с двумя полями: название до 160 и адрес до 300 символов. Backend убирает крайние/повторные пробелы, но не исправляет название и не разбивает адрес по запятым/точкам. Сервер формирует `Название · Адрес`. Вставку `Название | Адрес` можно распределить автоматически. Рядом совет выбирать общественное место и не указывать домашний адрес.

Миграция 0014 добавляет к прежнему Plan nullable place_name/place_address и поля проверки: place_revision, place_review_version, place_check_status, place_checked_revision/by/at/reason. Старые строки place/venue, даты и адреса Match/контекст отклика не переписываются и не разделяются догадками. Старые однопольные запросы совместимы, старые планы отображают place как прежде. Свободный ввод сохраняет прежний текстовый фильтр, дату в будущем, квоту, проверку автора и ограничения изменения при любой истории откликов/мэтче. Новый policy — free-place-v1, без ключей/ID каталога.

`pending` → «Место пока не проверено», `confirmed` → «Место проверено», `unconfirmed` → «Место не подтверждено». Отказ не скрывает план и не назначает санкцию. Проверка запрещённых тем и модерация самого плана остаются отдельными механизмами. Даже скрытие старого объекта каталога не блокирует публикацию нового плана. Неподтверждённый адрес не считается автоматически общественным или безопасным.

## Необязательная проверка после публикации

/admin → «Проверка мест»: очередь опубликованных/закрытых планов, фильтр статуса, название/адрес/план/имя автора. Для исторической строки показывается исходная строка без выдуманного разбиения. Прежнее разрешение moderation: moderator/admin/owner, не analyst/user. Нет свободного чтения анкет, фото или переписок.

Сотрудник сверяет данные по доступным источникам, указывает основание решения; для положительной отметки явно подтверждает наличие достаточных сведений. Не найденные/неоднозначные сведения — не основание для положительной отметки. Не добавляются обещания безопасности, наличия свободных мест или актуальных часов работы.

POST решения требует сессию, CSRF/Origin/account context, expected_revision и expected_version. Строка Plan блокируется FOR UPDATE; решение относится к точной версии места, сериализуется с редактированием. Название/адрес изменились → отметка сбрасывается атомарно, ревизия и версия проверки растут. Изменение описания/названия плана не сбрасывает подтверждение адреса. Решение не меняет Plan.version, согласованные условия и срок встречи. Чтение/решение пишутся в прежний AdminAuditLog; причина доступна уполномоченному сотруднику. Удаление сотрудника обнуляет reviewer FK, не удаляет план/аудит. Новых санкций или ролей нет.

## Три независимых признака

Единый компактный ReputationBadges используется в анкете, сведениях автора плана/кандидата и партнёра. При отсутствии данных ничего отрицательного не выводится; каждый признак объясняется отдельно. Проверка адреса показывается возле места, отдельно от репутации человека.

1. **Фото подтверждено** — прежний D65: действующее одобрение текущего фото/revision/content version. Смена фото, отзыв и прежние серверные ограничения работают как раньше. Эта задача не включает сбор самостоятельно и не меняет согласие, камеру, приватное хранение/удаление селфи или роли модерации
2. **Есть подтверждённые встречи** — прежний D58: DISTINCT партнёров по двум завершённым «Да», неотменённой встрече и прежней политике Survey. Повтор пары, молчание/разногласие/незавершённость не повышают показатель. Публично только отметка без числа; точный личный показатель — «Подтверждённые знакомства»
3. **Приятное общение** — число DISTINCT партнёров, оставивших хотя бы один положительный вариант после взаимно подтверждённой встречи, не меньше POSITIVE_IMPRESSIONS_THRESHOLD (по умолчанию 3). Это настройка backend, не клиентское число и не защита от накрутки

Новая таблица positive_impressions использует существующий составной ключ SurveyRecipient(survey_id, participant_side); отдельные копии пользователей/мэтчей/получателя не создаются. Поля pleasant/interesting/comfortable, версия осознанного согласия, created_at/updated_at. Всего 39 прикладных таблиц, head 0014. Партнёр вычисляется из Match, не передаётся клиентом.

Вопрос «Что понравилось в общении?» добровольный: «Приятно общаться», «Интересный собеседник», «Комфортная встреча»; несколько вариантов либо пропуск. До сохранения текст и отдельное подтверждение объясняют влияние на публичную отметку. Приватные старые rating/comment никогда не используются и не копируются в этот ответ. Индивидуальные варианты и имена авторов не выдаются партнёру/администратору; публичное API добавляет только boolean pleasant_communication в прежний Experience. Публичного числа положительных ответов нет. Прежнее числовое поле D58 сохранено для совместимости и личной статистики, публичный UI его не показывает.

Один и тот же партнёр учитывается один раз по всем встречам и вариантам. PUT заменяет только собственный ответ, повтор не создаёт дубликатов; DELETE удаляет только собственное положительное впечатление, повтор безопасен. Запись и исправление исходных ответов используют общий Survey FOR UPDATE, оба транспорта прежнего опроса совместимы. Исправление Да на Нет немедленно исключает вклад; восстановление взаимного Да снова делает сохранённый добровольный ответ подходящим. Отозвать своё впечатление можно и после потери взаимного подтверждения. Пропуск не создаёт запись и не штрафует. Отдельный срок для нового вопроса заданием не установлен: новый TTL не вводится; исходный B09 и его 7 дней не меняются.

## API

Все пути с `/api/v1`, прежние cookie/CSRF/account context.

| Метод | Путь | Назначение |
|---|---|---|
| POST / PATCH | /plans / /plans/{id} | Новые place_name/place_address, прежний place совместим; статусы проверки во входе запрещены |
| GET | Прежние API планов | place_name/place_address/place_check_status в PlanDTO; сохранён place |
| GET | /admin/place-checks | moderation, state/offset/limit, очередь и аудит |
| POST | /admin/place-checks/{plan_id}/decision | confirmed/unconfirmed, expected_revision/version, reason, evidence_confirmed |
| GET | /matches/{id}/impressions | Только участник: eligible, own_options, submitted, consent_version |
| PUT | /matches/{id}/impressions | Свои options, consent_accepted, consent_version=positive-impressions-v1 |
| DELETE | /matches/{id}/impressions | Отзыв только своего ответа |
| GET | /me/reliability и прежние контекстные анкеты | Прежний Experience + pleasant_communication boolean |

Лишние поля/попытки передать автора, участника, статус или положительный счётчик отклоняются. Неавторизованным 401, чужая встреча 404, без CSRF/не той роли 403, конфликт версии или отсутствие взаимного Да для нового положительного ответа 409.

## Запуск и ручная приёмка

```powershell
Set-Location C:\Users\arthur\Desktop\poidem
docker compose up -d --wait db
.\backend\.venv\Scripts\python.exe -m alembic -c .\backend\alembic.ini upgrade head
.\backend\.venv\Scripts\python.exe -m alembic -c .\backend\alembic.ini check
.\backend\.venv\Scripts\python.exe -m poidem --port 8001
# В другом PowerShell
Set-Location C:\Users\arthur\Desktop\poidem\frontend
npm.cmd run dev
```

Прежний Quick Tunnel → Vite 5173 → /api → 8001, PostgreSQL loopback, один бот. Никаких запросов/ключей внешних Places API; прежний каталог не надо наполнять ради публикации. Фотоверификация использует только ранее настроенные владельцем флаги.

Проверка A/B: A вводит название и адрес, сохраняет/публикует без проверки; B видит нейтральный статус и может откликнуться. Уполномоченный сотрудник проверяет адрес, A видит галочку. До появления откликов A меняет адрес → статус сбрасывается. После отклика/мэтча правка блокируется прежними правилами. Для репутации оба проходят прежний опрос по реальному времени, затем каждый независимо может оставить/изменить/отозвать впечатление. На двух аккаунтах нельзя проверить порог трёх разных партнёров — это покрывают автоматические тесты с синтетическими аккаунтами только в *_test БД. Не менять реальные даты/квоты/ответы для ускорения приёмки.
