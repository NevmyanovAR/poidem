# Этап 9Б — управление контентом, командой и диагностикой (D62)

Расширен прежний `/admin`; таблицы пользователей, роли в `users`, Telegram-сессии,
CSRF, аналитика D61, жалобы и outbox остаются единственными механизмами. Новое
задание утверждает редактор, пять ролей и диагностику; оно заменяет прежний запрет
D61 на эти конкретные функции. Новые санкции, изменение чужих анкет/договорённостей,
автоматические фотографии планов, рассылки, монетизация и полноэкранные фото не добавлены

## Возможности и права

| Функция | owner | admin | moderator | analyst | user |
|---|---|---|---|---|---|
| Обзор / аналитика / агрегированный CSV | Да | Да | Нет | Да | Нет |
| Информационные пользователи и планы / связанные действия | Да | Да | Нет | Нет | Нет |
| Жалобы / разрешённые доказательства / dismiss и hide_plan | Да | Да | Да | Нет | Нет |
| Редактор «Вдохновения», загрузка фото | Да | Да | Нет | Нет | Нет |
| Система / задачи уведомлений / общий аудит | Да | Да | Нет | Нет | Нет |
| Поиск пользователей в «Команде» / назначение и отзыв ролей | Да | Нет | Нет | Нет | Нет |

`GET /admin/session` возвращает текущие `role` и `permissions`. Каждый endpoint
самостоятельно перечитывает роль из БД; состояние открытого интерфейса не даёт прав.
Панель показывает только разрешённые разделы и перепроверяет роль при переходах,
возврате фокуса и каждые 30 секунд. Analyst не получает списки пользователей,
доказательства, приватные отзывы или общий журнал с административными идентификаторами

Права изменяются после подтверждения выбранного пользователя, роли и причины.
Общий PostgreSQL advisory transaction lock защищает HTTP и CLI от одновременного
снятия последних владельцев. Проверяются актуальная версия пользователя, active,
сессия/CSRF/контекст и право owner. Повтор уже выполненного изменения не пишет второй
аудит. Отозванная роль прекращает работать на следующем запросе той же сессии.
Удаление своего owner-аккаунта заблокировано до передачи и отзыва собственной роли;
это также не обходит сохранность истории B13. UI не создаёт сотрудников без Telegram-входа

## Назначить заказчицу первым владельцем

1. Заказчица входит в Mini App настоящим Telegram-аккаунтом. Username не доказывает
   её роль и не используется для назначения
2. Существующий администратор находит её в разделе «Пользователи», сверяет учётную
   запись и копирует полный внутренний UUID. Не используйте числовой Telegram ID
3. Доверенный оператор локально выполняет из корня проекта:

```powershell
Set-Location C:\Users\arthur\Desktop\poidem
$existingUserId = 'ПОДТВЕРЖДЁННЫЙ_UUID_ЗАКАЗЧИЦЫ'
.\backend\.venv\Scripts\python.exe -m poidem.admin --user-id $existingUserId --confirm-user-id $existingUserId --role owner --reason 'Назначение владельца доверенным оператором'
```

Нужен прежний локальный `MIGRATION_DATABASE_URL`; секреты не передаются в командной
строке. Миграция никого не назначает владельцем и не меняет роли прежних admin.
CLI сохраняет прежние user/admin и поддерживает owner/moderator/analyst, запрещает
снять последнего owner и записывает `server_assign_role` — действие оператора,
а не доказательство пользовательского нажатия

4. Заказчица открывает **Анкета → Настройки → Управление приложением → Команда**,
   находит уже вошедшего сотрудника по имени/UUID, выбирает роль и причину,
   проверяет подтверждение и сохраняет. Для отзыва выбирает «Пользователь»
5. Проверить на втором аккаунте доступные разделы; после отзыва повторить запрос
   без перезахода. Права должны пропасть. Не проверять на единственном владельце

Первый owner автоматически в ходе разработки не назначается

## Редактор и фотографии

Прежние `art-evening`, `slow-dinner`, `gallery-date` с исходными текстами, категориями,
фотографиями и порядком перенесены миграцией в `editorial_ideas`. Ссылки
`/create?idea=...` сохраняются. Статический frontend-fallback удалён: «Вдохновение»
читает только опубликованные идеи API; при ошибке есть повтор, а не подстановка копии

Редактор: название, описание, категория, место, название будущего плана, подпись
на фото, порядок; создание черновика, редактирование, загрузка/замена фото,
предпросмотр через общий компонент карточки, явная публикация/снятие и удаление
с подтверждением. Открытие редактора переводит к форме и фокусирует первое доступное
поле; не нужно искать форму под длинным списком. Адрес неизменяем после создания. Меньший порядок раньше,
одинаковый порядок разрешается адресом. Серверная пагинация по 25 (максимум 50)

Изменения уже опубликованной идеи и её фото видны после сохранения — это явно
подписано в редакторе. Отдельные версии черновиков поверх живой публикации не
придуманы. Перед публикацией нужны фото, название будущего плана и место.
Версия защищает от перезаписи параллельными редакторами. Пользовательский план
копирует поля идеи в обычную существующую форму, не становится редакционной записью

Фото проходят прежний `media.prepare_photo`: JPEG/PNG/WebP, до 3 МБ и 16 Мп,
один кадр, проверка соответствия MIME и содержимого, EXIF-ориентация, декодирование
и новое JPEG без метаданных. Проверены лимит HTTP-body, Origin/CSRF, полномочия
и версия. SVG/HTML/анимация/повреждённые файлы не выдаются как фотография

Редакционные фото явно предназначены для публикации. У них отдельная проверяемая
связь с идеей, без возможности присвоить фото чужого профиля. Публичный маршрут
возвращает фото только опубликованной идеи; preview требует editorial. Снятие
публикации прекращает последующую выдачу фото, но не может отозвать уже сохранённую
кем-либо копию. Исходные файлы профилей по-прежнему приватны

Фото записываются в общий постоянный `MEDIA_ROOT`, как прежде; в Docker это
`private-media`, не временный каталог контейнера. Сборщик orphan-файлов учитывает
ссылки редакционных идей. Замена/удаление использует прежнюю `media_deletions`.
У идеи сейчас нет FK из пользовательских планов; удаление идеи не меняет их сведения.
Удалённая или снятая идея по старой ссылке честно недоступна, без имитации содержимого

### Резервная копия

Сохраняйте **БД + весь MEDIA_ROOT**, включая редакционные фотографии, и соответствующую
версию репозитория с `frontend/public/images` для трёх исходных статических фото.
Нельзя считать один `pg_dump` полной копией приложения

Для согласованной локальной копии сначала остановите API и единственный bot/worker
через Ctrl+C в их окнах; PostgreSQL оставьте запущенным. Затем:

```powershell
.\backend\.venv\Scripts\python.exe scripts\backup_local.py --writers-stopped
```

Скрипт создаёт в игнорируемом `.local/backups` ZIP: `database.dump`, `media/*.jpg`,
manifest. Использует существующий Docker PostgreSQL `pg_dump` и не передаёт секреты
аргументами. Исходный dump оставляется отдельно; временный dump также остаётся в
контейнере. Он не считается проверенной копией без контрольного восстановления.
Скрипт не запускает/останавливает процессы, не публикует копии. Копия содержит
персональные данные: ограничить доступ, не коммитить, хранить отдельно от рабочего
диска по согласованной политике. Восстановление и проверка целостности — в отдельной
изолированной среде; не перезаписывать работающую БД без отдельного решения

Это команда для текущего запуска API/бота **из .venv на хосте**: читается MEDIA_ROOT
этого окружения. Для контейнерного API хостовый каталог не равен volume private-media.
В таком случае остановить writers, сохранив контейнер api, сначала скопировать
его MEDIA_ROOT, затем упаковать вместе с тем же снимком БД:

```powershell
docker compose --profile app stop api bot
$mediaCopy = Join-Path (Get-Location) ('.local\container-media-' + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $mediaCopy | Out-Null
docker compose --profile app cp api:/app/uploads/profiles/. $mediaCopy
if ($LASTEXITCODE -ne 0) { throw 'Копирование MEDIA_ROOT не завершено' }
$previousMediaRoot = $env:MEDIA_ROOT
try {
    $env:MEDIA_ROOT = $mediaCopy
    .\backend\.venv\Scripts\python.exe scripts\backup_local.py --writers-stopped
} finally {
    $env:MEDIA_ROOT = $previousMediaRoot
}
```

Путь внутри api соответствует текущему compose.yaml; при его изменении сверить
актуальный MEDIA_ROOT. `docker compose down` перед копированием не выполнять:
нужен существующий остановленный контейнер. Контейнерная процедура здесь описана,
но в этой задаче фактически не выполнялась

## Диагностика уведомлений и heartbeat

`notification_jobs` остаётся единственной очередью. Диагностика ничего не переотправляет

| Категория | Серверное основание |
|---|---|
| Успешно отправлены | state=sent |
| Ожидают отправки | pending/leased; retry с cooldown — ожидание интервала, не ошибка |
| Ожидают повторной попытки после ошибки | прочие retry |
| Намеренно пропущены | suppressed с известной сохранённой безопасной причиной |
| Окончательно не доставлены | failed |
| Причина неизвестна для старых записей | suppressed без причины / старый event_obsolete / нераспознанная причина |

Фактический локальный срез до изменений **26.11.2026**: 13 sent, 2 pending,
12 suppressed. Из этих 12:

- **7 bot_not_allowed:** не было разрешённой привязки к личному чату бота. Этот код
  не различает отсутствие привязки и её состояние, поэтому более точный вывод запрещён
- **2 notifications_disabled:** отправка отключена настройками пользователя или общей
  конфигурацией. Старый код не различает эти варианты
- **3 event_obsolete**, все chat_message: старая общая причина «событие утратило
  актуальность». Нельзя утверждать, что сообщения прочитаны, участники заблокированы
  или ответили: конкретное условие тогда не сохранялось

Ни одна из этих 12 не имеет state=failed/retry. После классификации интерфейс
покажет 9 намеренно пропущенных и 3 с неизвестной точной причиной. Записи не изменены
задним числом. Будущие подавления сохраняют конкретные коды: блокировка пары,
прочитано/ранее уведомлено, результат отклика изменился, план недоступен, опрос недоступен

Списки показывают тип, время создания/назначенной отправки/доставки, категорию,
попытки и безопасную причину с серверным фильтром/пагинацией. Нет получателя,
entity_ref, текста чата, callback, cookie или токена. Внутренние коды не показываются
пользователю как заголовки состояний

Два heartbeat в одной таблице `bot_heartbeats`: `polling` обновляется после
успешного возврата getUpdates, `worker` — живым циклом очереди не чаще раза в 10 с.
Свежесть 60 с, при ошибке цикла — error, при штатном завершении — stopped,
устаревший сигнал — stale, без записи — unknown. Последняя доставка отдельно.
Heartbeat не доказывает доставку каждого сообщения и не заменяет причины ошибок.
Никакого второго polling, отдельного мониторинга или отдельного сервиса нет

## Аналитика и аудит

Сохраняются все метрики, формулы и снимок JSON/CSV D61. Для первых публикаций API
добавляет `data_status` и фактическую `collection_started_at`. Если период начинается
раньше границы 0009, UI показывает «Неполные данные» и дату начала учёта; воронка
остаётся с доступной когортой откликов. NULL не превращается в ноль. Полностью
покрытый период без событий даёт настоящий 0. Возвращаемость остаётся «Нет данных»

Добавлены два снимка текущего состояния, без сравнения с прошлым периодом:

- **Опубликовано планов сейчас:** COUNT plans с publication_status=published и
  moderation_status ∈ прежний plans.VISIBLE_MODERATION (not_submitted/approved)
- **Доля текущих публикаций с откликами:** 100 × такие планы с EXISTS хотя бы одного
  plan_response / все такие планы. Пустой знаменатель → NULL. Не историческая конверсия;
  даты создания и прошедшее время встречи здесь не фильтруются

Старая метрика переименована в **«Доля созданных в периоде планов с откликами»**:
её знаменатель по-прежнему включает черновики. Новая её не подменяет. CSV содержит
оба показателя, определения и колонки полноты/начала учёта. Уникальные встречи D58
и публичный опыт не изменены

Общий аудит переключает значимые действия / чтение / все; прежние строки не удалены.
В подробностях пользователей/планов есть связанная история с серверным ограничением
контекста. Поиск планов дополнен автором (имя/полный UUID), остальные фильтры сохранены

## API и миграция

К прежним /api/v1 добавлены:

- `GET /admin/team`, `PUT /admin/team/{uuid}/role` — только owner
- `GET|POST /admin/inspiration`, `PUT /admin/inspiration/{slug}`,
  `POST /admin/inspiration/{slug}/command`, `POST|GET /admin/inspiration/{slug}/photo`
- `GET /inspiration`, `/inspiration/{slug}`, `/inspiration/{slug}/photo` — только
  опубликованный редакционный контент, без персональных данных; чтение без входа
- `GET /admin/notifications`, `/admin/audit` — ограниченные списки
- `GET /admin/plans` дополнен `author`, остальные endpoints 9А сохранены

Точный контракт — Pydantic/OpenAPI и `schemas/admin_management.py`. Все записи
требуют прежнюю серверную авторизацию, account context, CSRF/Origin и право функции

Миграция **0010**: расширить CHECK/длину role_code без изменения существующих ролей;
добавить `editorial_ideas` с тремя исходными идеями и `bot_heartbeats`. Всего 35 таблиц,
не вторая система пользователей. Downgrade явно остановлен, чтобы не удалять контент
и не преобразовывать роли автоматически; откат требует отдельного плана сохранения данных

Локально перед новым кодом остановить API и единственный bot/worker, затем:

```powershell
docker compose up -d --wait db
.\backend\.venv\Scripts\python.exe -m alembic -c backend\alembic.ini upgrade head
.\backend\.venv\Scripts\python.exe -m alembic -c backend\alembic.ini check
.\backend\.venv\Scripts\python.exe -m poidem --host 127.0.0.1 --port 8001
```

Frontend в другом PowerShell: `Set-Location frontend; npm.cmd run dev`.
Единственный бот — в отдельном окне: `.\backend\.venv\Scripts\python.exe -m poidem.bot`.
Не запускать его повторно при уже работающем polling. Временный HTTPS-стенд прежний:
Quick Tunnel → Vite 5173 → /api → 8001; PostgreSQL не публикуется

Команды повторения проверок из корня в PowerShell (не запускать pytest и test:auth
одновременно на одной тестовой БД):

```powershell
docker compose up -d --wait db-test
.\backend\.venv\Scripts\python.exe -X utf8 -m pytest backend\tests -p no:cacheprovider --basetemp=.local\pytest-admin9b
.\backend\.venv\Scripts\python.exe -m ruff check backend scripts\backup_local.py
.\backend\.venv\Scripts\python.exe -m ruff format --check backend scripts\backup_local.py
Set-Location frontend
npm.cmd run typecheck
npm.cmd run lint
npm.cmd run build
npm.cmd run test:production
npm.cmd run test:devices -- admin-dashboard.spec.ts admin-management.spec.ts
```

Флаг basetemp использован из-за недоступных старых каталогов Windows Temp;
pytest может очищать именно этот временный каталог внутри .local — не указывать
в нём фотографии, исходники, .env или каталоги рабочей базы
