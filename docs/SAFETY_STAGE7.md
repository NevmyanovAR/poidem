# Этап 7 — жалобы, персональные блокировки и модерация

D56 меняет только навигацию и оформление: актуальные настройки находятся в `/settings`,
список — `/settings/blocked`, вход через шестерёнку в шапке анкеты. Прежние права
этого этапа сохраняются. [Текущее размещение и проверки](SETTINGS_UX.md)

Основание: задание пользователя от 25.11.2026, D55. Существующие FastAPI, PostgreSQL,
Telegram-сессия, React-приложение и aiogram-очередь сохранены. Деморежим не возвращается

Фактическая основа этапа 6 проверена по коду и актуальным отчётам: polling/worker,
outbox, настройки уведомлений, deep links и согласованный опрос реализованы. Ранее
пользователь подтвердил на A/B `/start`, новое поступление отклика, отказ, принятие
одного мэтча у обоих, объединение десяти сообщений в одно уведомление и opt-out
с сохранением сообщения в приложении. Это не означает физическую проверку всех
ветвей опроса/Telegram API или нового оформления D54; автоматические проверки используют
подмену только Bot API и настоящую изолированную PostgreSQL

## Утверждённые правила

- Два уровня: прежний серверный фильтр планов, затем рассмотрение поступивших жалоб
  администратором. Прошедший фильтр план публикуется без обязательного ручного одобрения
- Жалоба не доказывает нарушение, не меняет рейтинг, не скрывает контент и не банит
- Личные блокировки запрещают новые отклики, принятие ожидающего отклика и сообщения
  между двумя людьми. Они не отменяют встречу, не меняют согласия/статусы и не удаляют историю
- Инициатор не видит планы заблокированного в каталоге; второй участник не получает
  уведомления о блокировке и видит нейтральное «Переписка недоступна»
- Разблокировка снимает только собственное ограничение. При встречной блокировке общение
  останется недоступным; отклики, согласия и мэтчи автоматически не создаются
- Ограничение действует внутри «Пойдём?». Приложение не управляет личными чатами Telegram
- B13 и D50–D54 сохранены: удаление аккаунта со связанными данными по-прежнему 409,
  окончательный отказ/15 ожидающих/архив через 7 дней/персональное скрытие без TTL

## Интерфейс

Меню «…» доступно у чужого плана, анкеты, входящего активного отклика и в шапке мэтча/чата.
По D57 отдельные сообщения больше не имеют меню и жалоб. «Пожаловаться» → причина, необязательный комментарий
до 1000 символов → «Отправить жалобу» → «Жалоба отправлена»

Причины: неподходящий контент, оскорбления или домогательства, мошенничество,
фейковая анкета, опасное поведение, другое. Серьёзная операция блокировки требует
подтверждения. Список разблокировки находится в «Моя анкета» → «Настройки безопасности»

Панель `/admin` использует прежний frontend и сессию. Очередь фильтруется по статусу
и объекту жалобы, имеет пагинацию. Детали показывают сохранённые доказательства,
комментарий и историю решений. Назначенному администратору доступна ссылка из настроек
анкеты. Прямое открытие адреса обычным пользователем не даёт прав

## API

Все маршруты имеют префикс `/api/v1`. Все требуют настоящей сессии; записи дополнительно
проверяют Origin, CSRF и переданный X-Account-Context. Автор/участник определяется сервером

| Метод / маршрут | Действие |
| --- | --- |
| POST `/reports` | Подать жалобу; 201 новая, 200 существующая |
| GET `/reports/{id}` | Только собственный краткий результат, без чужих жалоб/доказательств |
| POST `/me/blocks` | Идемпотентная персональная блокировка |
| GET `/me/blocks` | Только собственные активные блокировки |
| DELETE `/me/blocks/{id}` | Снять собственную блокировку, повтор 204 |
| GET `/admin/session` | Проверить серверную роль admin |
| GET `/admin/reports` | Очередь: state=pending/reviewed, target_type, cursor, limit 1–50 |
| GET `/admin/reports/{id}` | Доказательства только конкретной жалобы и её решения |
| GET `/admin/reports/{id}/photo` | Только фото, указанное в снимке жалобы на анкету |
| POST `/admin/reports/{id}/decision` | dismiss или hide_plan с обязательной причиной |

Жалоба и блокировка принимают `target_type: profile|plan|match|chat`,
`context_type: plan|response|match`, `context_id`. По D57 `message` и `message_id`
для новых запросов отклоняются с 422; чтение старых жалоб администратором сохраняется.
Комбинации проверяются сервером: план должен быть доступен и опубликован,
отклик принадлежать стороне, мэтч/переписка — самому участнику. Жалоба на собственный
контент и подмена участника запрещены. Поля telegram_id/user_id/role не принимаются

В жалобе дополнительно `reason_code: content|harassment|fraud|fake|danger|other`,
`comment` необязателен. Повтор на один объект/версию возвращает первоначальную жалобу,
а не меняет её комментарий. Изменённая анкета/план —
новая версия. Уведомления о жалобе проверяемому человеку не отправляются

Технический антиспам: 5 новых жалоб и 10 новых блокировок за минутное окно на пользователя;
повтор существующей операции не расходует окно. Это не продуктовая санкция.
`lock_actor` и UNIQUE защищают от конкурентных дублей

## Данные и права

Миграция **0008**, прежние 33 таблицы, без новой базы:

- reports: target_type/key, case_id и JSON evidence; UNIQUE(reporter_id,target_key)
- user_restrictions: kind=administrative/personal; уникальна активная направленная
  персональная блокировка, запрещена блокировка себя; lifted_at/by сохраняют историю
- moderation_cases/decisions и admin_audit_log используются для решения и аудита
- Старые жалобы/ограничения сохранены как legacy/administrative; автоматических санкций
  и массового удаления/перепривязки нет

В снимке плана — название/описание/место/время; анкеты — разрешённые имя/возраст/описание
и ссылка на ID фото, без Telegram ID/username. Старые жалобы на сообщения сохраняют
свои ограниченные снимки; по новой жалобе на переписку — три последних сообщения
на момент подачи. Общего административного API чтения чатов нет. Снимки и комментарии
хранятся в защищённой БД, а не в технических логах

Фото доступно по конкретной жалобе только пока соответствующий приватный файл/metadata
существует. Удалённый после смены фото снимок не восстанавливается. Автоматическая
проверка содержания фотографий/личности не реализована

В HTML интерфейса пользовательские строки выводятся React как текст. Нельзя передать
произвольный HTML, команду SQL или путь к файлу. Административная роль независимо
проверяется в каждом запросе, в том числе выдаче доказательств и фото

## Транзакции и уведомления

Новые взаимодействия и блокировка сериализуются advisory-lock одной пары. Блокировка
сразу помечает ещё не отправленные response/chat jobs suppressed, включая leased;
после разблокировки они не оживают. Worker повторно проверяет ограничения и держит
тот же pair-lock на время отправки: начатая до блокировки доставка может закончиться
до её фиксации, но после успешного ответа блокировки новая отправка не стартует.
Доставленное Telegram сообщение не отзывается. Опрос о встрече не является новым
взаимодействием между людьми и не отменяется персональной блокировкой

Для сериализации собственных записей пользователя используется PostgreSQL
`FOR NO KEY UPDATE`: это сохраняет взаимное исключение изменений аккаунта и совместимо
с FK KEY SHARE другого участника. Полный FOR UPDATE создавал цикл при параллельных
вставках блокировки/сообщения; исправление проверяется конкурентными тестами

Решение блокирует строку жалобы и проверяет актуальную версию плана. Повтор с той же
операцией/причиной идемпотентен; другая операция после решения — 409.
По устаревшим доказательствам новую редакцию плана скрыть нельзя. hide_plan меняет
только moderation_status=rejected и версию, сохраняет публикацию/мэтч/чат/историю;
обычное редактирование/повторная публикация не обходят существующий запрет модерации

## Безопасно назначить первого администратора — Windows PowerShell

Из корня репозитория, в локальном PowerShell с доступом к игнорируемому `.env`:

```powershell
Set-Location C:\Users\arthur\Desktop\poidem

.\backend\.venv\Scripts\python.exe -m alembic -c backend\alembic.ini upgrade head
.\backend\.venv\Scripts\python.exe -m poidem --host 127.0.0.1 --port 8001
```

В другом окне:

```powershell
Set-Location C:\Users\arthur\Desktop\poidem\frontend
npm.cmd run dev
```

Будущий администратор сначала входит в Mini App через Telegram. В консоли **своего**
Mini App можно получить только UUID учётной записи, не выводя cookie/initData/CSRF:

```javascript
fetch('/api/v1/me', { credentials: 'include' })
  .then(r => { if (!r.ok) throw new Error('Вход не подтверждён'); return r.json() })
  .then(data => console.log(data.user.id))
```

Оператор сверяет, что это учётная запись нужного человека, и запускает локально:

```powershell
$adminUserId = 'ПОДТВЕРЖДЁННЫЙ-UUID-ПОЛЬЗОВАТЕЛЯ'
.\backend\.venv\Scripts\python.exe -m poidem.admin --user-id $adminUserId --role admin --reason 'Назначение первого администратора локальным оператором' --confirm-user-id $adminUserId
```

Команда не создаёт пользователей, не принимает имя/username вместо UUID, не имеет HTTP
аналога. Используется локальный MIGRATION_DATABASE_URL, секреты не выводятся.
Аудит action=server_assign_role отличает назначение локальным оператором от решения
в панели; actor_id в такой записи — назначаемая существующая учётная запись

Для отзыва той же роли используйте `--role user` с причиной. Он действует на следующие
запросы уже открытой сессии; повторный вход не нужен. Для открытия панели в Telegram
перейдите из настроек анкеты или откройте `<текущий HTTPS-origin>/admin` **в том же Mini App**

Для временного HTTPS используется существующая инструкция [TELEGRAM_MANUAL_TEST](TELEGRAM_MANUAL_TEST.md):
Quick Tunnel → Vite 5173 → `/api` → настоящий backend 8001. PostgreSQL остаётся loopback;
адрес туннеля не закреплён в коде. Production/Pages/BotFather самостоятельно не меняются

## Сценарий рассмотрения

1. Пользователь отправляет жалобу из контекста доступного объекта
2. Администратор открывает «Новые», выбирает тип и конкретную жалобу
3. Изучает снимок и комментарий; наличие жалобы само по себе не подтверждает нарушение
4. Вводит причину: «Жалоба необоснованна» или для нарушающего плана «Скрыть план»
5. Для скрытия подтверждает действие. Решение видно в «Рассмотренных» вместе с актором,
   временем и причиной; страницы обновляются локально

## Ручная проверка A/B/C

Только тестовые аккаунты/контент. C — отдельно назначенный существующий admin

1. A публикует план, B открывает его анкету/план, отправляет жалобу и повторяет отправку
   (одна запись). A/B не могут читать чужую жалобу или административные endpoints
2. C открывает `/admin`, фильтрует жалобу, проверяет снимок, признаёт необоснованной с причиной
3. B жалуется на другой тестовый план A; C скрывает его. В каталоге план отсутствует,
   у автора сохраняется статус модерации. Реальные чужие планы не трогать
4. На отдельном плане A/B создают мэтч и переписку; B жалуется через меню в шапке чата, у отдельных сообщений меню нет
5. C видит максимум три последних сообщения из снимка жалобы; произвольный чужой чат ему недоступен
6. B блокирует A из чата: у обоих отправка запрещена и история видна; мэтч не отменён,
   новые отклики запрещены, планы A скрыты у B, отдельных оповещений о блокировке нет
7. Проверить бот: не доставляются ожидавшие и новые запрещённые response/chat уведомления
8. B разблокирует A из настроек: никакой новый мэтч/отклик не появляется; старые
   подавленные уведомления не возвращаются, переписка доступна при отсутствии встречного блока
9. Проверить встречную блокировку и её независимое снятие, повторные нажатия и отказ без CSRF
10. Повторить основной вход/сохранение анкеты/планов и проверить 320–430 px и desktop

Mocked Bot API и браузерные fixtures не означают настоящую доставку или проверку
на физических Telegram-клиентах. Ручной прогон этого этапа выполняется отдельно
