## Подтверждённые решения

- Возраст — целое число 18+, **без верхней продуктовой границы**. Целевая аудитория 18–27 не является ограничением. Проверка не удостоверяет фактический возраст. JSON ограничен точным представлением целых в JavaScript (`2^53−1`); это техническая граница, а не максимальный возраст продукта
- Удаление охватывает аккаунт «Пойдём?», анкету, фотографии, интересы, все сессии, собственную привязку бота и связанные собственные аналитические записи. Сам аккаунт Telegram не удаляется
- Frontend уже размещён пользователем на `https://poidem-demo.pages.dev`. Backend сейчас локальный. Адреса настраиваются; для этапа 3.5 разрешён и запущен временный Quick Tunnel, production и настройки Pages не менялись
- Настоящий HTTPS-вход на двух Telegram-аккаунтах проверен на этапе 3.5. Автоматизированные auth-тесты прежнего этапа используют синтетические подписи и отдельную PostgreSQL; они не подменяют ручной прогон. Актуальные test:tunnel работают с настоящим API 8001 и не имитируют успешную авторизацию

## Реализованный протокол

Frontend передаёт исходную строку `Telegram.WebApp.initData` без пересборки в `POST /api/v1/auth/telegram`. До загрузки внешнего SDK строка берётся из параметра запуска `tgWebAppData` в URL fragment: официальный SDK использует тот же источник. Декодируется только внешнее кодирование параметра, содержимое initData не пересобирается. При наличии SDK используется его initData. `initDataUnsafe`, отдельные ID/username и клиентские роли не используются как доказательство входа. Неизвестные JSON-поля запрещены.

Оптимизация D45 от 22.11.2026: проверка начинается до окончания сетевой загрузки SDK. При временной ошибке транспорта или HTTP 502/503/504 выполняется максимум один автоматический повтор на весь вход, включая проверку /auth/csrf. Оба запроса остаются обязательными; cookie другого пользователя не подтверждает вход. Ошибки 401/403/429 и сменившийся контекст не повторяются автоматически. HTML-ответ шлюза сохраняет HTTP-статус при обработке. Реальные задержки зависят от сети; прежний тайм-аут 10 секунд на запрос не является искусственной паузой и не уменьшался. При длительном сбое дополнительная попытка может увеличить суммарное ожидание.

Backend использует стандартные `hmac`/`hashlib` по [официальному алгоритму Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app): ключ HMAC выводится из bot token с ключом `WebAppData`; отсортированные `key=value` соединяются переводом строки, исключается только `hash`. Поле `signature`, если присутствует, участвует в этой HMAC-проверке. Это не сторонняя Ed25519-проверка. Сравнение выполняется через `compare_digest`.

До создания пользователя отклоняются дубли параметров, повреждённое кодирование, неверная подпись, неподходящие типы ID и устаревший/слишком будущий `auth_date`. Имя пользователя обновляется только из подписанных данных; внутренний UUID однозначно связан с подтверждённым Telegram ID. Конкурентные входы сериализуются по этому ID и ограничены UNIQUE в PostgreSQL.

После входа создаётся случайная opaque-сессия: токен только в HttpOnly cookie, в БД его SHA-256 hash. Cookie host-only, `Path=/`, без `Domain`; на HTTPS с Secure называется `__Host-poidem_session`. В памяти frontend остаётся только отдельный CSRF-токен. Записи требуют точного разрешённого Origin и `X-CSRF-Token`; чтение — действующей сессии. Открытых операций изменения по чужому user ID нет. Перевыпуск входа заменяет cookie; другие устройства сохраняют свои сессии до logout, истечения или удаления аккаунта.

Каждый новый Telegram-контекст сначала проходит проверку подписанной строки, даже при существующем cookie другого аккаунта. Frontend подтверждает приём cookie через `/auth/csrf`, проверяя возвращённый внутренний UUID. Запоздалые входы и сохранения от прежнего аккаунта не восстанавливают его данные на экране нового. Без SDK/строки обычный браузер не авторизуется автоматически и не падает. Ручной повтор входа может восстановить уже действующую серверную cookie-сессию.

Повторное использование ещё свежего initData допустимо для восстановления входа; оно не доказывает новое согласие на план. Нет автоматического доверия к фотографии из Telegram или проверки реальной личности.

## Анкета и фотографии

Сохраняются имя 1–40 символов, целый возраст 18+, текущие варианты пола/предпочтений формы, описание 1–300 символов, ровно три разных интереса и собственный `photo_id`. Справочники прежней формы выделены отдельно от демоанкет и добавлены миграцией; это не новые правила совместимости. `expected_version=0` создаёт анкету, последующие сохранения передают текущую версию; конфликт — 409.

Загрузка принимает один JPEG/PNG/WebP до 3 МиБ и 16 мегапикселей. Проверяются MIME, реальный формат, целостность и декодирование; анимация отклоняется. Сервер применяет EXIF-ориентацию и сохраняет новый JPEG с длинной стороной до 2048 px, без исходных EXIF/ICC/комментариев. Имена файлов генерируются сервером. Такая проверка содержимого проверяет изображение технически; модерация и проверка лица не заявляются.

Файлы лежат вне `frontend/public`: нативно `uploads/profiles`, в Docker — private volume. Фото сейчас доступно **только владельцу** через защищённый API. Выдача кандидатам появится с согласованными правилами публикации. Статус обработки `ready` не означает одобрение модератором.

Замена и удаление ставят файловую очистку в устойчивую очередь PostgreSQL. После удаления аккаунта все сессии недействительны сразу; ответ 200 означает завершённую очистку, 202 — отложенный повтор удаления файлов. Очередь повторяется при работе API/после перезапуска. Осиротевшие файлы незавершённых записей проверяются с часовым запасом. Используйте один и тот же MEDIA_ROOT для всех процессов API с этой БД: не запускайте нативный API и Docker API с разными каталогами фотографий одновременно.

Для будущих совместных планов/мэтчей/истории модерации политика удаления ещё не утверждена. Если такие связанные записи уже появились административно, удаление возвращает 409 `ACCOUNT_HAS_RELATED_DATA` **до любых изменений**. Оно не стирает чужую историю каскадом. До подключения бизнес-API необходимо согласовать эту политику (B13).

## Настройки и локальный запуск

Секреты находятся только в игнорируемом корневом `.env`. В `.env.example` настоящих токенов/паролей нет. Токен, ранее присланный в чат, не переносился в команды или исходники; перед реальным тестом рекомендуется перевыпустить его через BotFather и ввести локально без отображения:

```powershell
# Из корня репозитория, после первичного создания .env по backend/README.md
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Set-TelegramToken.ps1
```

Скрипт запрашивает скрытый ввод и заменяет только TELEGRAM_BOT_TOKEN в `.env`. Не передавайте значение параметром командной строки. Если токен отсутствует, API запускается, но настоящий login возвращает безопасный 503 `TELEGRAM_AUTH_UNAVAILABLE`.

| Переменная | Назначение / локальное значение |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | Только backend, скрытый ввод локально |
| `MINI_APP_URL` | Канонический адрес приложения; сейчас `https://poidem-demo.pages.dev` |
| `API_PUBLIC_URL` | Канонический внешний адрес API, пока пусто; не создаёт маршруты/прокси |
| `VITE_API_BASE_URL` | Публичный base URL frontend-клиента, включая `/api/v1`; никогда не секрет |
| `POIDEM_API_PROXY_TARGET` | Локальный Vite proxy; по умолчанию `http://127.0.0.1:8001` |
| `POIDEM_DEV_ALLOWED_HOSTS` | JSON-массив точных дополнительных имён для будущего dev-туннеля; по умолчанию `[]` |
| `CORS_ORIGINS` | JSON-массив точных origins без путей; localhost/127.0.0.1:5173/:4173 для разработки |
| `TRUSTED_HOSTS` | Разрешённые имена HTTP Host; локально localhost/127.0.0.1 |
| `INIT_DATA_MAX_AGE_SECONDS` | 300 секунд, технический настраиваемый срок свежести |
| `AUTH_CLOCK_SKEW_SECONDS` | 30 секунд допуска в будущее; часы сервера должны быть синхронизированы |
| `SESSION_TTL_SECONDS` | 86400 секунд, срок сессии, не продлевается каждым чтением |
| `SESSION_COOKIE_SECURE` | Пусто: auto true для production, false для local; для HTTPS-туннеля true |
| `SESSION_COOKIE_SAMESITE` | `lax` локально / на одном сайте; `none` требует Secure |
| `MEDIA_ROOT` | Приватный каталог; относительный путь считается от корня репозитория |
| `PHOTO_MAX_BYTES/PIXELS/EDGE` | 3145728 / 16000000 / 2048; frontend сейчас показывает лимит 3 МиБ |
| `LOGIN_REQUESTS_PER_MINUTE` | 30 успешных подписанных попыток на подтверждённый TG ID за минуту |
| `PHOTO_REQUESTS_PER_MINUTE` | 10 загрузок на авторизованный UUID за минуту |

Последние два ограничения — техническая защита, не бизнес-квоты 3/15. Ошибочные неподписанные запросы ограничены размером тела и дешёвой проверкой до БД; полноценная защита публичного ingress от потока запросов относится к размещению. Шифрование транспорта и ограничение общего потока нужно настроить перед пилотом.

```powershell

.\backend\.venv\Scripts\python.exe -m pip install -r .\backend\requirements-dev.lock
.\backend\.venv\Scripts\python.exe -m pip install --no-deps -e .\backend
.\backend\.venv\Scripts\python.exe -m alembic -c .\backend\alembic.ini upgrade head
.\backend\.venv\Scripts\python.exe -m poidem
```

API — `http://127.0.0.1:8001`, Swagger — `/docs`. В другом PowerShell:

```powershell
Set-Location C:\Users\arthur\Desktop\poidem\frontend
npm ci
npm run dev
```

Frontend — `http://127.0.0.1:5173/`. В dev пустой VITE_API_BASE_URL означает `/api/v1` через локальный Vite proxy. В production пустое значение **отключает реальный API**; опубликованный статический frontend не получает сервер автоматически. После изменения VITE-переменных необходима новая сборка. Ни текущая ссылка Pages, ни переменная API_PUBLIC_URL не перенаправляют `/api` самостоятельно.

## Единственный источник пользовательских данных

Frontend монтирует только ApiProvider, использует useAppData. DemoProvider, переключатель, заполнение примером, вымышленные анкеты/публикации/отклики/мэтчи/надёжность и имитация согласий удалены. Настройка URL или старый localStorage-флаг не возвращают их. При старте удаляются только ключи симуляции poidem:simulation:v1 и переключателя poidem:demo-mode:v1. Старый обычный профиль poidem:demo:v1 (несмотря на историческое имя) не читается/не импортируется; он удаляется только после явной локальной очистки или удаления аккаунта. Открытие неизвестного человека/мэтча показывает безопасное пустое состояние.

Настоящие анкета/фото/сессия — на сервере, frontend хранит ответы и ввод в памяти. До API планов пользовательские черновики временные, каталог пуст. Редакционные идеи сохранены в data/editorial.ts, общие справочники в data/catalogs.ts; они не выдаются за пользовательские публикации. Подтверждённый локальный сброс очищает временные черновики и старые данные прототипа, сохраняя серверную анкету; удаление аккаунта — отдельное подтверждаемое действие.

## Будущая проверка в Telegram на двух аккаунтах

Эти шаги подготовлены, но ещё не выполнялись. Локальный HTTP API недоступен телефону через публичный Pages и не подходит для HTTPS Mini App. Нельзя проверять настоящий вход через синтетический API `serve_test_api.py`/порт 8002.

1. Перевыпустить и локально ввести токен нужного бота; запустить **настоящий** backend на 8001 с основной локальной БД. Не публиковать PostgreSQL. Выбрать временный HTTPS-доступ или тестовый хостинг отдельно
2. Для одного origin можно вручную туннелировать локальный Vite (5173), который проксирует `/api` в 8001. Добавить точный hostname туннеля в POIDEM_DEV_ALLOWED_HOSTS, его HTTPS origin в CORS_ORIGINS, задать SESSION_COOKIE_SECURE=true, SameSite=lax, MINI_APP_URL и API_PUBLIC_URL согласно выбранному адресу. Backend Host после dev proxy остаётся локальным. Никакого автоматического прокси в Pages при этом не появляется
3. Если используется существующий Pages и отдельный HTTPS API: задать VITE_API_BASE_URL=`https://<api-host>/api/v1` при отдельной сборке, разрешить `https://poidem-demo.pages.dev` в CORS_ORIGINS и hostname API в TRUSTED_HOSTS, SESSION_COOKIE_SECURE=true и SameSite=none для разных сайтов. Это требует отдельной публикации по разрешению пользователя. Safari/iOS может всё равно блокировать сторонние cookie; предпочтительнее проверенный один origin или same-site домены. Клиент обнаруживает неприём cookie и не показывает ложный успешный вход
4. В BotFather вручную настроить Main Mini App либо menu button `/setmenubutton` на выбранный HTTPS frontend по [инструкции Telegram](https://core.telegram.org/bots/webapps#launching-mini-apps). Открывать приложение как Mini App из бота; обычный переход браузером не создаёт initData. Настройки бота в рамках этой работы не менялись
5. Аккаунт A: открыть Mini App, дождаться серверного подтверждения; заполнить собственную анкету/фото, закрыть и открыть снова. Сохранённая анкета должна восстановиться; отредактировать и проверить ещё раз
6. Аккаунт B: повторить со своей анкетой и фото. Анкета A не появляется. Обращение B к UUID фото A даёт 404, без сессии — 401. Проверить отсутствие настоящих профилей в localStorage, закрытые Cookie и отсутствие raw initData в логах; не копировать их в отчёт
7. На A выполнить локальную очистку черновиков: серверная анкета и сессия сохраняются после повторного входа. Переключателя и заполнения примером нет; старые флаги/ссылки не показывают вымышленных людей. B не затронут
8. На A удалить аккаунт «Пойдём?»: исчезают профиль/фото/все его сессии, на другом его устройстве /me даёт 401. Новый вход A создаёт пустой аккаунт, данные B сохраняются. Сам Telegram-аккаунт не удаляется
9. Проверить iPhone и Android, закрытие/повторный запуск и позднюю загрузку SDK. Истечение initData проверять повторным открытием после превышения TTL, не отправляя сырую строку через чат. Зафиксировать фактически пройденные устройства/адреса без секретов

До этих действий автоматизированные тесты не доказывают реальную доставку initData клиентами Telegram, работу HTTPS-туннеля или политику cookie на конкретном iPhone.

После test:auth пересоберите обычный frontend перед production-регрессией: auth suite использует собственную конфигурацию API при сборке.
