# Этап 5: окончательный отказ, чат, архив и список «Все»

23.11.2026, D50. Работа поверх реализованного D49, без второй системы пользователей,
планов или авторизации. Предыдущий отчёт [MATCHES_STAGE5](MATCHES_STAGE5.md) — история
первоначального этапа; разрешение повторного отклика после отказа отменено.
Удалённый ранее DemoProvider не восстанавливается. Вымышленные данные — только тесты.

## Подтверждённые правила и реализованное поведение

- До 15 **одновременно ожидающих** откликов от разных людей. Пользователь отдельно
  подтвердил: отказ освобождает место другим людям, отклонённому повтор запрещён
- Один отклик на пару `(plan_id, responder_id)` за всю историю. Повтор сетевого запроса
  не создаёт новую запись. После отказа даже прежний Idempotency-Key не даёт повторного
  согласия. Статус отказа — `rejected`, API-команда `decision: decline` сохранена
- Отклонённому план немедленно недоступен на сервере: каталог, детали, capacity,
  публичная анкета и её фото. Это сохраняется после нового входа и изменения названия.
  Другие планы автора доступны. В истории отправителя остаётся результат отказа,
  без анкеты/карточки/ссылки на скрытый план; глобальной блокировки нет
- Принятие под блокировкой строки плана создаёт ровно один Match, ChatThread и две
  позиции прочитанности. План закрывается, остальные ожидания получают `closed`
  («Пара уже выбрана»). UNIQUE и транзакция запрещают вторую пару
- Встроенный чат двух участников работает независимо от Telegram username. Текст
  до 2000 символов, время, история, пагинация, unread и восстановление после открытия
- Telegram — дополнительная кнопка «Написать в Telegram», только если подтверждённый
  username даёт безопасную ссылку. Нет требования настроить username и ссылок по ID
- Отмена немедленно переносит план в архив. Другие планы — через семь календарных дней
  после времени встречи **в IANA-зоне плана**, включая DST. Бизнес-статус не меняется
  автоматически на «встреча состоялась»; рейтинг и факт встречи не записываются
- Архив сохраняет отклики, мэтч и переписку. «Скрыть»/восстановить меняет только
  представление конкретного пользователя, без удаления или отмены встречи

Вкладка «Все» формируется сервером в следующем порядке:

| Группа | Внутренний порядок |
| --- | --- |
| Мэтчи | Время встречи по возрастанию, индикатор unread |
| Входящие ожидания, доступные для решения | Новые сверху |
| Собственные опубликованные планы | Ближайшие даты сверху |
| Отправленные ожидания | Последние отправленные сверху |
| Черновики | Последние изменённые сверху |

Мэтч заменяет отдельную карточку собственного закрытого плана в «Все». Отменённые,
архивные, скрытые и отклонённые отправленные отклики сюда не попадают. До семидневной
границы история остаётся доступна без утверждения, что встреча состоялась. Для
результатов отказа есть прежняя вкладка «Выбранные», для архива — отдельная вкладка.

## API

Base `/api/v1`. Все перечисленные ресурсы требуют действительную сессию. Запись —
Origin + CSRF; `X-Account-Context` проверяет совпадение окна с серверным аккаунтом,
не является доказательством входа. Автор/отправитель не принимаются из JSON.

| Метод и путь | Поведение |
| --- | --- |
| GET `/plans/{id}/author`, `/author/photo` | Прежний защищённый публичный контекст; rejected закрывает доступ |
| GET `/plans/{id}/capacity` | Число ожидающих, максимум 15, оставшиеся места |
| POST `/plans/{id}/responses` | `expected_plan_version`, UUID `Idempotency-Key`; 201/200, rejected → 409 `RESPONSE_REJECTED` |
| GET `/me/responses?direction=incoming\|outgoing` | Прежняя история; rejected отправителю имеет `plan:null`, `profile:null` |
| POST `/responses/{id}/decision` | `expected_version`, `decision:accept\|decline`; отказ окончательный |
| GET `/me/matches`, `/matches/{id}` | Прежние мэтчи + `unread_count`, `archived`, `meeting_cancelled` |
| GET `/matches/{id}/contact` | Безопасный username контакт только участнику; отсутствие не мешает чату |
| GET `/matches/{id}/chat` | Состояние чата/прочитанности, unread, разрешение отправки, архив/отмена |
| GET `/matches/{id}/messages` | История, `limit=1..50` (default 30), `before` **или** `after` |
| POST `/matches/{id}/messages` | `{client_id:UUID,text:string}`, 201 новый / 200 повтор |
| POST `/matches/{id}/read` | `{through_sequence:integer}`, монотонная позиция текущего участника |
| GET `/me/activity` | Единый список, `scope=active\|archive`, `include_hidden`, `cursor`, `limit=1..50` |
| POST `/me/archive/{plan_id}/visibility` | `{hidden:boolean}`, 204; только собственная архивная карточка |

История сообщений: `items` в возрастающем `sequence`, `next_before` для ранней
страницы, `has_more` для продолжения. Без курсора — последние сообщения. `after`
возвращает следующие по порядку, а не последние: при накопившихся сообщениях клиент
дочитывает все страницы. DTO: `id`, `sequence`, `sender:self|other`, `text`, `created_at`,
`client_id` только у собственных сообщений. Telegram ID/sender_id/приватные медиа не выдаются.

Повтор сообщения с тем же `(match_id, sender, client_id)` возвращает ту же запись;
с другим текстом — 409 `MESSAGE_RETRY_CONFLICT`. Ключ сохраняется в строке сообщения,
не истекает через сутки. Отправитель определяется из сессии. Серверный технический
антиспам — `CHAT_MESSAGES_PER_MINUTE=30` на аккаунт, 429 и Retry-After. Это настраиваемое
ограничение транспорта, не бизнес-квота знакомств. HTML отображается React как текст.

Вкладка «Все»: SQL UNION ALL, общий порядок `(priority, ordering, UUID, kind)`,
keyset-пагинация после объединения; descending-время нормализуется отрицательным epoch.
Курсор содержит scope/hidden и проверяется по типам/диапазонам. Фильтры доступа
применяются заново на каждой странице; курсор не выдаёт прав. Клиент не пересортировывает
первую страницу и не копирует всю БД: отображает полученные страницы и «Показать ещё».
В архиве на участника одна карточка плана/своего отклика/мэтча, а не копии согласий.

## Данные и миграция

`backend/migrations/versions/0005_chat_archive_final_rejection.py`, head `0005`.
33 таблицы, четыре новые:

| Таблица/поле | Ограничения и назначение |
| --- | --- |
| plan_responses | Полный UNIQUE(plan_id,responder_id); `declined` перенесён в `rejected`; частичные accepted/slot индексы сохранены |
| plans.updated_at | Серверное время изменения для сортировки черновиков |
| plans.archived_at | Отдельная метка архива и индекс; бизнес-статус не подменяется |
| chat_threads | PK match_id → matches RESTRICT, счётчик последовательности |
| chat_messages | FK thread/users RESTRICT, UNIQUE(match_id,sequence), UNIQUE(match_id,sender_id,client_id), длина 1..2000 |
| chat_read_states | PK(match_id,role), две роли автора/откликнувшегося, монотонный read cursor |
| archive_hidden | PK(user_id,plan_id), FK RESTRICT; только персональное скрытие |

Старые мэтчи получают пустые чаты/позиции чтения. Старые отменённые и уже истёкшие
планы получают метку архива. Аккаунты, фото, планы, согласия и сообщения не удаляются.

**Защита старой истории D49:** если в другой БД уже есть несколько попыток одной пары
plan/responder, upgrade остановится **до изменений**, а не удалит/объединит историю
ради UNIQUE. Потребуется отдельно согласовать перенос таких записей. В текущей
локальной основной БД перед миграцией таких пар было 0. Downgrade намеренно запрещён,
чтобы не потерять переписку; volume/основная БД не очищались.

Отправка сообщений сериализуется строкой ChatThread, отклики и принятие — строкой Plan.
Сохраняется существующая блокировка текущего аккаунта/проверка живой сессии. Новый чат
создаётся в той же транзакции, что мэтч и закрытие остальных ожиданий.

Архив: фоновая asyncio-задача в lifespan FastAPI, цикл раз в 60 секунд, идемпотентный
UPDATE. Работает без открытого клиента. После простоя API догоняет просроченные планы
при запуске. Чтения используют то же календарное условие немедленно, не ждут тика.
Несколько API-процессов безопасно повторяют UPDATE. Брокер/WebSocket/новый сервис не нужны.

## Frontend и безопасность

Существующие ApiProvider/ApiClient, cookie и CSRF сохранены. Новые компоненты:
`Chat.tsx`, `ActivityFeed.tsx`, `PlanCards.tsx`; доработаны MyPlans/Match/Catalog и типы.
Существующие карточки выделены в компоненты без глобального редизайна. Новые стили
используют прежние токены; PNG, фото, Nicoletta/Forum, приветствие/home не изменены.
Насыщенный голубой не добавлялся: сохраняется действующий утверждённый интерфейс.

Чат опрашивается раз в 3 секунды только в активном видимом окне; при возврате приложение
догружает пропущенное. Лента/каталог/индикаторы откликов обновляются раз в 10 секунд
на соответствующем экране. Серверный запрет rejected действует сразу; устаревшая
карточка в открытом клиенте не позволяет открыть анкету/отправить согласие.

Read cursor обновляется для показанных сообщений у нижнего края истории, не из
произвольного last_sequence, полученного при фоновом запросе. При чтении ранних
сообщений прокрутка не прыгает к концу. История и draft сообщения не пишутся в storage.
После смены аккаунта/маршрута запоздалые ответы не должны попадать в новое окно.

Технические логи не содержат body сообщения/сырые авторизационные данные. Чужой match_id
даёт 404 для истории/отправки/прочитанности. При ограничении второго аккаунта/плана
отправка закрыта, история активному участнику сохраняется без открытия чужих полей.
Публичные фото по-прежнему выдаются только в проверенных контекстах; старый приватный
`/media/photos/{id}` остаётся owner-only. Это не модераторская система блокировок.

## Ручная проверка двумя настоящими аккаунтами — ожидает подтверждения

1. A/B открыть кнопку Mini App, дождаться подтверждённого входа, проверить разные анкеты
2. A создать/опубликовать тестовый будущий план; B найти его, открыть анкету и откликнуться
3. A открыть «Полученные отклики», отклонить B. B обновить каталог: плана нет;
   старая ссылка на его карточку недоступна, в «Выбранные» есть только результат отказа
4. B закрыть/открыть Mini App: запрет сохраняется. Другой опубликованный план A виден.
   Четвёртый план за московский день не создавать: прежняя квота 3 продолжает действовать
5. A создать второй план; B откликнуться; A принять. У обоих одна и та же пара;
   «Все» ставит её выше публикаций/ожиданий/черновиков
6. Оба открыть «Открыть чат», отправить разные тестовые сообщения, проверить время,
   обновление без кнопки, unread в «Моих планах» и прочитанность после открытия чата
7. Закрыть/открыть Mini App, проверить историю; прокрутить ранние страницы при наличии
   более 30 сообщений (антиспам 30/мин не отключать). Проверить длинный текст/переносы
8. На аккаунте без username чат должен работать, Telegram-кнопки нет. Если оба аккаунта
   с username, отдельную такую проверку пока отметить «не выполнена». Наличие/смена
   username меняет только дополнительную ссылку после нового подписанного входа
9. A отменить **отдельный план без откликов**: сразу архив, нет в «Все»/каталоге. Скрыть,
   показать скрытые, восстановить; у другого пользователя ничего не удаляется
10. Архив мэтча проверить после календарной границы или отдельно на изолированной
    тестовой среде с управляемым временем. Не менять часы ОС/дату БД ради реального теста,
    не редактировать основную БД вручную. Автотест уже проверяет DST/семь дней и чат
11. Для архивного мэтча открыть чат, проверить сохранение переписки и персональность
    скрытия. Чужую приватную переписку проверять третьим тестовым аккаунтом только при
    его наличии; автоматизированная отрицательная проверка уже включена

Снимки/сообщения должны содержать только тестовые данные. До личного подтверждения
пользователя этот ручной прогон **не считается завершённым**. Прежняя успешная проверка
настоящей Telegram-авторизации на двух аккаунтах не заменяет новые сценарии.
