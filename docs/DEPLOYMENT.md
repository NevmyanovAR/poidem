# Подготовка демоверсии к Cloudflare Pages

Уточнение пользователя после подготовки: восстановлен белый основной текст с голубыми выделениями; брендовые HEX-коды фона и акцентов сохранены. Служебные пометки и пояснения о версии убраны из интерфейса и metadata. Это уточнение заменяет прежнее требование о сплошном светло-голубом тексте и видимой плашке «Демоверсия». Техническая документация ниже сохраняет сведения о локальной природе приложения и историю проверок.

Дата: 17.11.2026. Изменения только во frontend, конфигурации статического хостинга, проверках и документации. Коммиты, GitHub push, создание проекта Cloudflare и публикация не выполнялись.

## Что готово

Девять экранов React + TypeScript + Vite работают как статическое приложение. Анкеты, идеи и сценарии отделены в `frontend/src/data/demo.ts`; имена и описания вымышлены, фотографии — прежние иллюстрации из презентации. «Демоверсия» обозначена на приветствии и внутренних страницах. Настоящие персональные данные, токены и API-ключи не добавлялись.

Приложение не требует backend, PostgreSQL, бота, переменных окружения или Telegram initData. SDK загружается асинхронно и не блокирует обычный мобильный браузер; его отсутствие допустимо. Мэтч требует отдельного нажатия «Имитировать ответное согласие», не возникает автоматически от одностороннего приглашения.

## Настройки Cloudflare Pages

| Поле | Значение |
| --- | --- |
| Project name | `poidem-demo` — либо своё имя с синхронным изменением name в wrangler.toml |
| Framework preset | `React (Vite)` |
| Production branch | `main` — либо фактическая основная ветка |
| Root directory | `frontend` |
| Build command | `npm run build` |
| Build output directory | `dist` |
| Node.js | актуальная версия ветки 22, выбранная файлом `frontend/.node-version` |
| Environment variables / secrets | не требуются |

`dist` указывается относительно `frontend`, поэтому здесь нельзя подставлять `frontend/dist`. Итоговая папка на диске репозитория — `frontend/dist`. Сборка использует зависимости, зафиксированные в `frontend/package-lock.json`; TypeScript и другие devDependencies нужны во время сборки.

Добавлены два конфигурационных файла:

- `frontend/.node-version`: ветка Node.js 22; для локальной работы рекомендуется 22.13+.
- `frontend/wrangler.toml`: имя проекта и `pages_build_output_dir = "./dist"`. Нет Functions, bindings, account ID, токенов и серверных переменных. Wrangler устанавливать для публикации через GitHub/dashboard не требуется.

Конфигурация Wrangler фиксирует каталог артефактов, но не заменяет настройку Root directory и Build command в Git-интеграции. См. [Cloudflare: build configuration](https://developers.cloudflare.com/pages/configuration/build-configuration/), [build image и Node.js](https://developers.cloudflare.com/pages/configuration/build-image/), [Wrangler configuration](https://developers.cloudflare.com/pages/functions/wrangler-configuration/).

## Публикация владельцем через GitHub и Cloudflare

Ниже инструкция для ручного выполнения после просмотра результата. В рамках задачи эти действия не выполнялись.

1. Создайте репозиторий GitHub или используйте существующий. Можно выбрать private: Cloudflare поддерживает подключение репозитория через GitHub App. Для нового локального Git-репозитория из корня проекта выполните `git init -b main`; для существующего пропустите этот шаг.
2. Проверьте состав файлов. В коммит входят исходники frontend, конфигурации, package-lock и документация. `node_modules`, `dist`, test-results, реальные `.env` и `.wrangler` исключены через `.gitignore`.
3. Создайте коммит и отправьте его в свой репозиторий. Пример, который нужно адаптировать под свой GitHub и существующие remote/ветку:

   ```powershell
   git add README.md AGENTS.md .gitignore .env.example docs frontend references
   git diff --cached --stat
   git commit -m "Prepare Poidem frontend demo for Cloudflare Pages"
   git remote add origin https://github.com/YOUR_ACCOUNT/poidem.git
   git push -u origin main
   ```

   Если `origin` уже существует, используйте его; не добавляйте remote повторно. Сами PDF нужны для исходных материалов репозитория, но не попадают в публикуемый `dist`.
4. В Cloudflare откройте **Workers & Pages → Create application → Pages → Connect to Git**. Выберите GitHub, предоставьте доступ к нужному репозиторию, выберите его и перейдите к **Begin setup**. Названия экранов могут локализоваться; нужен именно Pages-проект с Git-интеграцией.
5. Заполните поля из таблицы выше. Серверные значения из корневого `.env.example` не переносите: демоверсия их не читает. Если имя `poidem-demo` занято, выберите доступное и предварительно измените `name` в `frontend/wrangler.toml`.
6. После проверки настроек выберите **Save and Deploy**. Этот шаг действительно начнёт публикацию. Дождитесь успешной установки зависимостей и `npm run build`; конечный публичный адрес вида `https://<имя-проекта>.pages.dev` покажет Cloudflare. В рамках подготовки этот адрес не создавался.
7. На опубликованном адресе откройте главную, `/catalog`, `/inspiration`, `/profile` и `/people/demo-gallery` напрямую, затем обновите страницы. Пройдите анкету, создание плана, приглашение и отдельную имитацию мэтча; обновите URL мэтча в том же браузере. Данные localStorage привязаны к адресу сайта: локальная и опубликованная версии имеют разные хранилища.
8. После настройки Git-интеграции последующие push могут запускать новые deployment/preview. Публикуйте обновления осознанно через выбранную ветку. Если сборка не прошла, исправляйте причину по build log; не добавляйте серверные токены ради статического frontend.

Порядок подключения и момент начала публикации сверены с [официальной инструкцией Git integration](https://developers.cloudflare.com/pages/get-started/git-integration/).

## Прямые ссылки и SPA

Используется BrowserRouter и стандартный SPA fallback Cloudflare Pages. При отсутствии top-level `404.html` Pages отдаёт корневое приложение для пути, не соответствующего статическому файлу. Поэтому `/catalog`, `/people/...`, `/match/...` должны загружаться и после обновления браузера. Не добавляется широкое правило rewrite, способное перехватить JS, CSS или фотографии. Поведение описано в [Serving Pages](https://developers.cloudflare.com/pages/configuration/serving-pages/).

Локальные production-проверки обслуживают готовый `dist` через Vite preview. Они проверяют прямые запросы и перезагрузки, но не заменяют проверку фактического deployment Cloudflare после ручной публикации.

## Аудит палитры

Подтверждённые цвета: бордовый `#550707`, голубой `#0599F6`, светло-голубой `#B8E4FF`. Единственное место определения основных токенов интерфейса — `frontend/src/theme.css`. Для `theme-color`, favicon и отдельной SVG-заглушки повторены те же точные значения; Telegram-оболочка читает бордовый из CSS-токена.

| Найдено в предыдущей версии | Исправление |
| --- | --- |
| Бордовый `#500e22`, дополнительные винные поверхности `#5d172a`, мобильная панель `#430a1cf7` | Основной фон и непрозрачные поверхности/навигация — `#550707`. |
| Голубоватый `#b4dcf2`, hover `#d0eafb` | Светло-голубой — `#B8E4FF`; основной интерактивный голубой — `#0599F6`. |
| Кремовый текст `#f7eddf`, `#faf0e4`, белые hover-надписи | Текст на бордовом — точный `#B8E4FF`; на голубых и светло-голубых элементах — `#550707`. |
| Приглушённые розовые подписи/placeholder `#d2b2ba`, `#c69fa9` | Единый светло-голубой; второстепенность сохраняется размером/расположением, а не ухудшением контраста. |
| Розовые ошибки и предупреждения `#f3b5a5`, `#ffc7b7`, `#f5dacb` | Бордер/акцент ошибки голубой, поясняющий текст светло-голубой; предупреждение светло-голубое с бордовым текстом. |
| Отдельные оттенки границ, теней, затемнений фотографий, модального фона | Семантические токены прозрачности только от трёх фирменных цветов. Случайные самостоятельные оттенки удалены. |
| Прежние цвета в Telegram chrome, theme-color, favicon и fallback.svg | Те же утверждённые значения, согласованные с общей палитрой. |
| Белые нативные индикаторы даты и времени в Chrome | Цвет индикаторов взят из светло-голубого токена через CSS-маски, без изменения размеров и поведения полей. |

Просматриваются приветствие, оба шага анкеты, главная, каталог, карточка человека и ожидание ответа, создание/предпросмотр, мои планы, вдохновение, мэтч и диалог общения. Отдельно проверяются hover, focus, selected и ошибки валидации. Размеры, расположение, шрифты и JPEG-фотографии не изменялись. Самостоятельные цвета фотографий не перекрашиваются: прозрачные затемнения и текст поверх них проверяются визуально.

Прозрачность декоративных границ, теней и зерна не вводит новых фиксированных фирменных HEX-кодов; она строится от тех же токенов. Основной текст не приглушается дополнительным цветом.

Расчёт контраста по относительной яркости sRGB:

| Текст / фон | Контраст |
| --- | --- |
| `#B8E4FF` / `#550707` | ≈ 10,97:1 |
| `#550707` / `#0599F6` | ≈ 4,86:1 |
| `#B8E4FF` / `#0599F6` | ≈ 2,26:1 — для обычного текста не используется |

Первые две пары превышают минимум 4,5:1 для обычного текста. Это не заявление о полном аудите WCAG: расчёт однотонных пар не доказывает контраст текста на каждой точке фотографии. Критерий — [WCAG 2.2, Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

Для тестов нужен установленный Google Chrome. Production-конфигурация Playwright сама запускает preview на `http://127.0.0.1:4173/` и останавливает его после прогона; приложение в браузере не использует Playwright.

## Что остаётся демонстрационным

Регистрация не создаёт Telegram-аккаунт и не подтверждает возраст. Подбор работает по вымышленным анкетам и статическим сценариям; нет реальной аудитории и загрузки с сервера. Сохранённые планы не публикуются, согласия и мэтчи имитируются локально. Кнопка общения объясняет будущий переход, не открывает чужой профиль и не отправляет сообщения. Уведомления, бот, опросы, административная аналитика, PostgreSQL и серверная авторизация отсутствуют. Перезагрузка сохраняет данные только в том же браузере; другой человек их не видит.
