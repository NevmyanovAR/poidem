# Этап 9 — кабинет управления и аналитика (D61)

Продолжение: [этап 9Б / D62](ADMIN_STAGE9B.md) расширяет роли, редактор, диагностику и методику текущих публикаций. Ниже сохранён отчёт исходного этапа 9А

Продолжение прежнего `/admin`, а не вторая панель. Пользователь подтвердил шесть разделов,
агрегированную аналитику, информационные списки, прежнюю модерацию и CSV. Расширенные
санкции/апелляции, редактирование чужих анкет/встреч, назначение ролей в UI, рассылки,
монетизация и редактор «Вдохновения» в этот этап не входят

## Разделы и доступ

- **Обзор:** показатели, предыдущий сопоставимый период, график регистраций/действий,
  очередь жалоб и переход к рассмотрению
- **Аналитика:** определения, категории, когортная воронка, пять исходов опросов,
  ограничения источников. Периоды 7/30/90 дней и произвольные 1–366 дней
- **Пользователи:** поиск по имени/полному UUID приложения, состояние аккаунта,
  даты регистрации, наличие/состояние анкеты, количество планов/мэтчей, связанные жалобы
- **Планы:** название, категория, время/зона встречи, публикация/модерация, автор
  (имя и UUID), даты создания, отклики; поиск/состояния/категория/даты/наличие жалоб;
  подробности содержат только поля плана и переход к жалобам
- **Модерация:** прежняя очередь/доказательства/итог конкретной встречи/решения
  `dismiss` и `hide_plan` с обязательной причиной и аудитом. Добавлены фильтры причины
  и связи с пользователем/планом. Скрытие по-прежнему ставит moderation_status=rejected,
  не меняет договорённости и не удаляет переписку. Старые жалобы на сообщения читаются,
  новые жалобы на отдельное сообщение по-прежнему запрещены D57
- **Система:** факт успешного ответа API/запросов PostgreSQL, состояния outbox,
  последняя сохранённая доставка, просроченная очередь и безопасные коды ошибок,
  последние 20 административных операций. Worker/polling **Нет данных**: heartbeat нет;
  очередь/прошлая доставка не доказывают, что процесс сейчас работает

Desktop — боковая навигация; mobile — компактные шесть кнопок. Большие декоративные
заголовки, пользовательский footer/нижняя панель и плавающий плюс в кабинете не нужны.
Основные страницы и их пять разделов D60 сохраняются. Палитра кабинета — прежние
#550707/#B8E4FF/белый; #0599F6 только для линии данных в admin.css по новому заданию,
не возвращается в пользовательские экраны. PNG/шрифты/фотографии не изменены

Все endpoints проверяют настоящую сессию, контекст аккаунта и `active + role_code=admin`
на сервере. Экспорт требует прежний Origin/CSRF. Списки ограничены 25 (API 1–50) строками,
поиск/сортировка/фильтры/total/pagination выполняются PostgreSQL. Курсоры каталогов
привязаны к роли текущего пользователя, виду списка и набору фильтров/сортировки

В списках нет Telegram ID/username, токенов, контактных сведений, фото/биографии,
свободного просмотра чатов или личных оценок/комментариев опросов. Фото/небольшие
доказательства/минимальный итог встречи доступны только через прежнюю конкретную жалобу.
API подробностей пользователя/плана и аналитики фиксирует факт чтения; экспорт — запрос
выгрузки. Аудит не утверждает, что браузер физически сохранил файл

## Периоды, снимок и методика

По умолчанию **Europe/Moscow**. В API поддерживаются корректные IANA-зоны; записи хранятся
в UTC. Даты аналитики включают начальный и конечный календарные дни выбранной зоны,
но текущий день обрезается фактическим временем снимка. Предыдущий интервал смежный,
заканчивается ровно перед текущим началом и имеет ту же длительность в UTC: нет
пересечения/двойного учёта при переходе на зимнее время. В JSON/CSV есть точные границы
`from / to_exclusive / previous_from / previous_to_exclusive`, зона и `generated_at`

Списки пользователей/планов имеют отдельный явно подписанный фильтр дат создания в UTC.
Срез аналитики считается последовательно в одной PostgreSQL REPEATABLE READ транзакции
через существующий pool. Это не второй backend/БД/кеш. UI экспортирует полученный от
сервера CSV и одновременно устанавливает возвращённый из того же расчёта JSON-снимок:
числа совпадают даже при изменении данных между обычным чтением и экспортом. На время
экспорта фильтры блокируются

| Показатель | Формула и источник | Ограничение/сравнение |
|---|---|---|
| Всего пользователей | COUNT(users) в снимке | Только существующие аккаунты, не восстановленная история удалений; без дельты |
| Новые пользователи | COUNT users.created_at ∈ период | Регистрации существующих аккаунтов; сравнение с предыдущим интервалом |
| Активные по действиям | COUNT DISTINCT actor из UNION ALL: plans.author_id/created_at, plan_responses.responder_id/created_at, matches.author_id/created_at (принятие), chat_messages.sender_id/created_at | Telegram-входы, чтение, просмотры, профильные правки и изменяемый последний ответ опроса сюда не входят; это не полный DAU по открытиям |
| Созданные планы | COUNT plans.created_at ∈ период | Включает черновики; повтор команды не создаёт новую запись |
| Первые публикации | COUNT уникальных D61 plan_published.occurred_at ∈ период | Только новые реальные переходы draft → published после установки 0009; если период не покрыт учётом целиком — NULL/«Нет данных», прежняя публикация не восстанавливается по updated_at |
| Отклики | COUNT plan_responses.created_at ∈ период | Одна строка кандидат/план; повторный HTTP-запрос не новая активность |
| Мэтчи | COUNT matches.created_at ∈ период | Один Match на план, согласованная модель этапа 5 |
| Подтверждённые встречи | COUNT DISTINCT Match.id с meeting_starts_at ∈ период, после +2 ч, не отменённый Plan, Survey текущей D53 policy, оба ответа submitted + met=true | Это встречи, а не уникальные партнёры публичного опыта; повторная встреча той же пары считается отдельной встречей; текущий исправленный результат, не журнал прежних ответов |
| Жалобы в очереди | COUNT reports WHERE state=pending сейчас | Вне фильтра периода; не признак установленного нарушения; без выдуманного сравнения |
| Планы с откликами | 100 × созданные в периоде планы с EXISTS plan_responses / все созданные планы периода | В знаменателе также черновики; исходы на дату снимка |
| Принятые отклики | 100 × accepted среди откликов, созданных в периоде / все отклики этой когорты | Состояние когорты сейчас; разное время ожидания, поэтому процент «роста» между когортами не выводится |
| Возвращаемость по открытиям/D1/D7 | NULL / «Нет данных» | Журнала открытий/использования и определения retention нет; входы не подменяют эти события |

В процентных долях нулевой знаменатель → NULL, не 0%. Процент изменения счётчиков =
100 × (текущий − предыдущий) / предыдущий; при предыдущем 0/неполном учёте → NULL,
без «бесконечного роста». Снимки total/pending и доли когорт не выдаются за рост

График: COUNT пользователей по дню регистрации и DISTINCT actor по дню действия в выбранной
зоне; отсутствие зарегистрированных действий в дне — достоверный 0 по этой методике.
Категории — COUNT созданных в периоде plans по category_code. Неинструментированные
открытия/прежние публикации/время в приложении/реальное физическое общение восстановить нельзя

### Воронка

Единица **одна пара кандидат/план**, не смесь количества людей и сообщений. Каждая
следующая ступень — подмножество предыдущей. Конверсия = 100 × числитель / знаменатель,
и оба числа возвращаются API/CSV

Если весь период после границы учёта 0009: первая зарегистрированная успешная запись
просмотра пользователем чужого доступного плана в периоде → последующий отклик этой пары
(created_at ≥ времени просмотра) → связанный Match → EXISTS ChatMessage этого Match →
подтверждённый результат этой встречи **после начала переписки**. Все исходы на дату снимка

Если период целиком не покрыт просмотрами: первая ступень NULL, конверсия из просмотров
не рассчитывается; доступная цепочка начинается с когорты откликов, созданных в периоде,
затем связанный Match / наличие переписки / взаимное Да после переписки. Подпись когорты
явно другая. Подтверждённые встречи без встроенного чата остаются в общих итогах встреч,
но не увеличивают последний переход последовательной воронки

Результаты встречи: mutual_yes / mutual_no / conflicting / insufficient / no_data —
по двум завершённым ответам прежней модели, для дат встреч периода и только после +2 ч.
Незавершённый ответ/молчание не превращается в Нет. Нет санкций или изменения D58/D59

## События, миграция и API

Новых таблиц нет, всего 33. **0009** добавляет четыре индекса created_at/id (users,
plans, matches, chat_messages) и один неперсональный marker measurement:D61 в прежнюю
analytics_events. Marker фиксирует границу, не backfill; downgrade не удаляет события

- `plan_published`: в существующей транзакции настоящего draft → published
- `plan_detail_view`: отдельный CSRF-защищённый POST после успешной загрузки чужого
  плана/анкеты; сервер повторно проверяет доступ. Собственные/недоступные планы не считаются
- UNIQUE event_key: D61/type/подтверждённый user UUID/plan UUID; повтор/конкурентная
  отправка не увеличивают число. Это зарегистрированное открытие, не доказательство,
  что человек внимательно посмотрел на экран. Сетевая потеря не дополняется вымыслом
- allowed_dimensions содержит только policy, без текстов/фото/initData/IP

| API | Назначение |
|---|---|
| GET /api/v1/admin/analytics | start_date, end_date, time_zone → агрегированный снимок |
| POST /api/v1/admin/analytics/export | Та же модель периода → {report,csv,filename}, CSRF и аудит |
| GET /api/v1/admin/users | q/state/since/until/sort/direction/cursor/limit → items/total/next_cursor |
| GET /api/v1/admin/users/{uuid} | Минимальные сведения/счётчики/число связанных жалоб, аудит |
| GET /api/v1/admin/plans | q/state/category/moderation/has_reports/since/until/sort/direction/cursor/limit |
| GET /api/v1/admin/plans/{uuid} | Контент плана/автор/метаданные, аудит; мутаций нет |
| GET /api/v1/admin/system | Только измеряемые системные сигналы и ограниченный аудит |
| POST /api/v1/plans/{uuid}/view | Разрешённый пользователь, не админская привилегия; actor из сессии |
| GET /api/v1/admin/reports | Прежний API + reason_code/user_id/plan_id для связанных жалоб |

В API нет создания/блокирования/удаления пользователей, выдачи ролей или свободного
чтения переписок/фотографий. Обычный пользователь → 403, без сессии → 401. Неподдерживаемый
POST /admin/users → 405, а не способ назначения роли. Неизвестный/чужой контекст просмотра
не создаёт событие. CSV — UTF-8 BOM, `;`, кавычки, защита строк с формулами Excel;
периоды/зона/методики/числители/знаменатели/снимок, без персональных выгрузок

## Локальный запуск и вход существующего администратора

Production/Pages не меняются. В PowerShell из корня проекта:

```powershell
Set-Location C:\Users\arthur\Desktop\poidem
docker compose up -d --wait db
# Остановить прежний API Ctrl+C до миграции и перезапустить после неё
.\backend\.venv\Scripts\python.exe -m alembic -c backend\alembic.ini upgrade head
.\backend\.venv\Scripts\python.exe -m poidem --host 127.0.0.1 --port 8001
```

В отдельном PowerShell:

```powershell
Set-Location C:\Users\arthur\Desktop\poidem\frontend
npm.cmd run dev
```

Frontend http://127.0.0.1:5173/admin; API http://127.0.0.1:8001. Без настоящей
Telegram-сессии локальная страница не даёт административных данных. В Mini App открыть
анкету → настройки → существующую «Панель модерации» (теперь кабинет), либо /admin на
том же разрешённом HTTPS-origin. Старый временный стенд: Quick Tunnel → Vite /api → 8001;
PostgreSQL на loopback, 8002 не используется. Самостоятельного production-размещения нет

Если роль уже admin, назначать её повторно не требуется. Роль не выдаётся по username,
клиентскому Telegram ID или переключателю. Только существующий доверенный CLI оператора:

```powershell
$existingUserId = 'ПОДТВЕРЖДЁННЫЙ_UUID_ПОЛЬЗОВАТЕЛЯ'
.\backend\.venv\Scripts\python.exe -m poidem.admin --user-id $existingUserId --confirm-user-id $existingUserId --role admin --reason 'Назначение доверенным оператором'
```

Эта инструкция описывает существующий механизм; автоматически роли не назначались
